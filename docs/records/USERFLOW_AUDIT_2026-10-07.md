## 5. mock이 실제 서버와 달라서 결함을 가리는 곳

SPEC_API §12.1은 "mock은 실패 케이스까지 실제 계약을 따른다"인데, 아래에서 어긋납니다. **🔴 4건이 모두 여기에 해당합니다** — mock으로 개발하고 테스트하면 통과하고, 실서버에서만 깨집니다.

| 영역 | mock | 실제 | 관련 |
|---|---|---|---|
| 비밀번호 변경 오류 field | `currentPassword` | `password` | 🔴-1 |
| 게시물 목록·상세 | 임시저장 글도 포함, 고정 우선 정렬 안 함 | 임시저장 제외, 고정 우선 | 🔴-2 |
| 알림 항목 형태 | `{id, message, read}` | `{type, refId, subject}` | 🔴-3 |
| 역할 변경 | PASTOR 지정 성공 + 실제로는 안 바뀜(no-op) | 400 | 🔴-4 |
| 계정 삭제 | 자기 삭제 허용, 카카오 계정은 안 지우고 성공 | 자기 삭제 400, 실제 삭제 | |
| 글 수정 slug | 유지 | 제목으로 재생성 | 🟠-10 |
| 첨부 20MB 초과 | `STORAGE_LIMIT`(409) | `VALIDATION_ERROR`(400), 8MB 초과는 500 | 🟠-9 |
| 가입 명단 확인 | 형식 검증 없음, 동명이인 field `null` | 형식 검증, field `"name"` | 🟡-5 |
| 새가족 등록 | rate limit·honeypot·검증 없음 | 있음 | |
| 리셋 코드 | 하이픈 강제, 0/O/1/I/L 섞임 | 하이픈 선택, 혼동 글자 제외 | 🔵-14 |
| 월례회 viewReason | 항상 `PERIOD_CLOSED` | `PERIOD_NOT_STARTED`도 있음 | 🟡-9 |

> 제안: 위 항목들을 mock에 반영하고, mock과 실제 응답 모양을 비교하는 계약 테스트를 하나 두면 같은 종류의 결함을 막을 수 있습니다.
