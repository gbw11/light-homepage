# PM 결정 기록

PM(프론트엔드·인프라·기획 총괄)이 대화 중 구두로 전달한 스펙 결정·변경사항을
모아두는 로그다. **여기 있는 항목은 PM이 별도로 다시 요청하지 않아도, 결정이
나올 때마다 자동으로 추가된다** (`frontend/docs/HARNESS.md` §1 규칙).

목적: 백엔드 담당자를 포함해 이 대화에 없었던 사람도, 왜 화면/기능이 이렇게
바뀌었는지 나중에 추적할 수 있게 한다. `docs/spec/SPEC_FUNCTIONAL.md`/
`docs/spec/WIREFRAME.md`의 확정 스펙과는 별개로, **아직 그 문서에 반영되지 않은
최신 결정**을 여기서 먼저 확인할 수 있다.

형식: 최신 항목이 위에 온다.

## 2026-09-04 — 주보 열람을 **회원 전용(M)으로** 되돌린다 (2026-08-25 공개 열람 전환 대체)

**결정**: 주보(`/bulletin`)는 **로그인해야 볼 수 있다.** 업로드·삭제는 그대로 임원(L).
구현: BE PR #168 (커밋 `88141c6`), FE 대응 대기 중.

| | 이전 | 이후 |
|---|---|---|
| `GET /api/bulletins/latest` · `?page=` · `/{id}` | `G` (비로그인 200) | **`M`** (비로그인 **401**) |
| `POST` · `DELETE /api/bulletins` | `L` | `L` (변경 없음) |

**무엇을 대체하는가.** 2026-08-25에 "주보 공개 열람 전환"이 결정돼 있었다. 그 결정은
`DECISIONS.md`에 항목으로 남지 않고 **FE 코드 주석 세 곳에만** 적혀 있었다
(`app/bulletin/page.tsx` · `app/home/page.tsx` · `lib/api/mock.ts`). 이번 결정이 그것을
대체한다.

**2026-08-31 재설계와의 관계.** 그때 "열람 M 복귀"로 내부공지·회의록·사진첩·월례회가
`M`으로 돌아갔는데 **주보만 예외로 남아 있었다.** 이번 결정으로 자료 화면의 열람 권한이
전부 `M`으로 일치한다 — 예외가 하나 있는 상태가 사고를 부른다.

**막힘은 401이다.** 예산안(§10 주의 2)의 `403`·`404`와 다르다. 주보가 있다는 사실 자체는
비밀이 아니라 "로그인하면 볼 수 있습니다"로 안내해야 하고, FE는 기존 `MemberGate`
흐름을 그대로 탄다.

**⚠️ FE 대응이 필요하다** — 지금 `/bulletin`에 게이트가 없어서, 비로그인 방문자는
`BulletinScreen`이 뿌리는 **"로그인이 필요합니다." 회색 에러 텍스트만** 본다.
로그인 버튼도 안내도 없다. 고칠 곳 4개(게이트 · mock 가드 · 내비 그룹 · 홈 링크)를
`FE_이슈_주보_회원전용.md`로 전달했다. **FE 대응 전까지 `develop`에 올리지 않는다.**

**반영된 문서** (모두 같은 값으로): `SPEC_API §10` 인가 매트릭스 · `SPEC_API §5.1~§5.3`
권한 표기 · `BACKEND_TASKS §6` 매트릭스 · 역할 설명표(GUEST 목록에서 주보 제거) ·
엔드포인트 표.

**실측**: 비로그인 latest·목록·상세 전부 401 → 회원 200 → 회원 업로드 403 →
공개 경로(공개공지·설교)는 그대로 200.

**결정 3건** (프론트엔드만, 백엔드 영향 없음). 구현: PR #158

그려지지 않고 있었고**, 값 하나로 동시에 켜졌다.

⚠️ PM이 준 주소의 공유 추적 파라미터(`?igsi=…`)는 **떼고 넣었다.** 공유 경로를

### ② 외부 링크에 목적지 이모지

`▶️ YouTube` · `📷 Instagram` · `⛪ 김해교회 홈페이지`. 전에는 셋 다 같은 `▸`를
달고 나란히 있어 어디로 가는지 글자를 읽어야 알 수 있었다. `aria-hidden`으로
감싸 스크린리더에는 링크 글자만 남는다. 사이드레일의 기하 기호(`▶` `◎`)도 같은

### ③ LIGHT 워드마크를 녹색 계열로

**LIGHT의 원래 로고가 녹색**이라는 PM 확인에 따라 워드마크를 녹색으로 둔다.
표면에 따라 토큰이 갈린다:

| 위치 | 토큰 | 대비 |

| 〃 다크 모드 | `--color-yellow` 다크 `#b3b792` | 8.32:1 AA |

홈 Hero의 아크로스틱 첫 글자가 이미 같은 토큰이라 색이 맞물린다.

**⚠️ 범위: "LIGHT 글자만"이다** (PM이 선택지 중 확정). 강조색(CTA 버튼·활성

문장이 조각나 보인다. `나의 LIGHT`(헤더 버튼 · `/my` 제목 · 뒤로가기 6곳) ·

타입이라 공용 컴포넌트를 고쳐야 한다). PM 확인 후 이어서 반영.

**스펙 문서 반영 상태**: `WIREFRAME.md`에 워드마크 색 지정이 없다. 헤더를
다음에 손볼 때 §3(디자인 토큰)과 함께 반영 필요.

## 2026-09-02 — 내비 하위 목록은 **마우스를 옮기면 닫힌다**

**결정**: 상위 메뉴(`소개`·`자료` 등)를 눌러 하위 목록이 펼쳐진 뒤, 마우스를
메뉴 밖으로 옮기면 목록이 사라진다. 전에는 열린 채로 남아 흐름이 이상했다.

- **영역**: 프론트엔드만. 백엔드 영향 없음.
- **왜 남아 있었나**: 마우스로 상위 항목을 누르면 링크에 포커스가 남고, 목록이
  `group-focus-within`으로 열려 있어서 hover가 풀려도 계속 참이었다. `자료`는
  클릭 토글이라 아예 상태로 열려 있었다.
- **어떻게 고쳤나**: `group-focus-within` → `group-has-[:focus-visible]`.
  브라우저는 **Tab 이동에만** `:focus-visible`을 주고 마우스 클릭에는 주지
  않으므로, 키보드 접근성(NFR-A11Y — hover만으로 열면 키보드가 닿지 못한다)은
  그대로면서 마우스를 옮기면 닫힌다. `자료`는 포인터가 떠날 때 상태를 내린다.
- **함께 고친 것**: `자료` 하위 링크를 누르면 닫는다. 클라이언트 이동은 헤더를
  다시 만들지 않아 **도착한 화면에서도 목록이 펼쳐진 채로** 보였다.
- **구현**: `frontend/src/components/layout/Header.tsx` — PR #153

## 2026-09-02 — 헤더 오른쪽에 **로그아웃**을 둔다 (데스크톱)

**결정**: 로그인한 회원이 내비바 오른쪽에서 바로 로그아웃할 수 있게 한다.
전에는 `/my`(나의 LIGHT)까지 들어가야 나갈 수 있었다.

- **영역**: 프론트엔드만. **백엔드 영향 없음** — 기존 `POST /api/auth/logout`을
  그대로 쓴다 (새 엔드포인트·계약 변경 없음).
- **자리**: `나의 LIGHT` 바로 오른쪽. 로그인 상태에서만 그린다. 로그인은 헤더
  오른쪽 한 번인데 로그아웃은 두 단계라 대칭이 맞지 않았다.
- **⚠️ 데스크톱(`lg` 이상)만이다.** 모바일 헤더는 워드마크·☎·나의 LIGHT·햄버거가
  이미 한 줄을 채워서, 글자를 더 넣으면 44px 터치 영역이 서로 붙는다
  (NFR-A11Y-05). 좁은 화면의 로그아웃은 **전체 메뉴 안에 이미 있다** — 없던 것을
  만든 것이 아니라 데스크톱에만 없던 것을 메웠다.
- **모양**: 링크가 아니라 `button`이다(이동이 아니라 상태 변경). 보조 동작이라
  `text-white/70`으로 한 단계 낮췄다 — `나의 LIGHT`가 계속 주 진입점이다.
  누르면 세션을 비우고 홈(`/`)으로 보낸다.
- **스펙 문서 반영 상태**: `WIREFRAME.md` 헤더 항목에 로그아웃 자리가 없다.
  헤더를 다음에 손볼 때 함께 반영 필요.
- **구현**: `frontend/src/components/layout/Header.tsx` — PR #151

**⚠️ 다음에 같은 함정을 피하려면**: 버튼에 `hidden lg:inline-flex`를 직접 걸었더니
`lg:inline-flex` 규칙이 CSS에 생성되지 않아 `hidden`만 남고 **데스크톱에서도 안
보였다**(실측: `getComputedStyle().display === "none"`, 해당 미디어 규칙 없음).
이 파일이 이미 쓰는 `hidden lg:block`을 감싼 `span`에 걸어 해결했다. 반응형
표시/숨김은 **그 파일에서 이미 동작하는 클래스 조합**을 쓰는 것이 안전하다.

## 2026-09-02 — 브랜치 규약은 **사람의 기억이 아니라 CI가 검사한다** (Branch Policy 워크플로)

**결정**: 작업 브랜치가 올바른 통합 브랜치를 향하는지 GitHub Actions가 매 PR마다
검사한다. 어긋나면 빨간 X와 함께 고치는 법을 띄운다.

    feat/fe-*    · fix/fe-*    ──▶  frontend_develop
    feat/be-*    · fix/be-*    ──▶  backend_develop
    feat/infra-* · fix/infra-* ──▶  server_develop

**배경**: 9/1에 FE PR 6건(#128 #129 #130 #131 #132 #134)이 `frontend_develop`을
우회해 `develop`으로 직행했다. 아무도 막지 않았고 **아무 신호도 없었다.** 그 결과
`frontend_develop`이 22커밋 뒤처져 #139로 따로 정리해야 했다. 규약을 사람의 기억에
맡기면 조용히 새어나간다 — Jenkins에서 시크릿 검사를 Actions로 옮긴 것과 같은 판단.

- **영역**: 공통(인프라). BE·FE 모두 PR을 열 때 영향받는다.
- **검증**: 셀프테스트 PR #143으로 **실패하는 것까지 눈으로 확인**하고 머지 없이
  닫았다. 위반(`fix/fe-*`→`develop`)은 FAILURE, 정상(`feat/infra-*`→`server_develop`)은
  SUCCESS. 실패 로그가 워크플로 오류가 아니라 의도한 안내문임을 확인했다.
- **한계(알고 들어간다)**: **머지를 막지는 못한다.** Free 플랜 private 저장소라
  branch protection이 403 — required check로 걸 수 없다. 빨간 X가 할 수 있는 전부다.
  Pro로 올리면 required check로 승격할 것.
- **예외**: 핫픽스 등 일부러 우회할 때는 PR에 `skip-branch-policy` 라벨.
  예외를 없애면 사람들이 검사를 통째로 지우기 때문에, 두되 **라벨로 눈에 보이게** 한다.
- **검사 대상 아님**: `docs/**` 브랜치 · 통합 브랜치→`develop` · `develop`→`main`.
  규칙 없는 조합까지 막으면 정상 흐름이 멈춘다.
- **구현**: `.github/workflows/branch-policy.yml` — PR #142(→`server_develop`) ·
  #144(→`develop`, `8d43daa`). 근거 문서는 `INTEGRATION.md` §6.3·§6.5.

## 2026-08-27 — 서버 최적화: **콜드스타트·재배포 요청 유실·풀이 만든 두 번째 과금 누수**

**결정**: 배포된 서버를 4가지 축으로 손본다 — ①새벽 첫 방문자의 콜드스타트
②재배포 중 요청 유실 ③512MB 안에서의 메모리 여유 ④**Neon 자동 정지와 커넥션
풀의 상호작용**. 비용은 늘지 않는다(오히려 ④는 과금 누수를 막는다).

- **영역**: 인프라(`server_develop`) + 백엔드 설정(`application.yml`) + 테스트 1개 신규
- **★ ④가 이번의 가장 큰 발견이다 — 8/27 오전에 막은 누수가 한 군데 더 있었다**:
  핑 경로를 `/actuator/health/alive`로 옮겨 "HTTP 요청이 DB를 깨우는" 길은
  막았는데, **커넥션 풀이 같은 일을 하고 있었다.** HikariCP 6.3.3의
  `keepaliveTime` 기본값이 0이 아니라 **2분**이어서 유휴 커넥션에 2분마다
  쿼리를 보내고, `minimumIdle` 기본값이 `maximumPoolSize`와 같아 풀이 **고정
  크기 3개**로 절대 비워지지 않는다. 결과: **서버가 깨어 있는 558h/월 동안
  Neon도 깨어 있다.** `keepalive-time: 0` · `minimum-idle: 0` ·
  `idle-timeout: 240000`(Neon 정지 5분보다 먼저)으로 고쳤다
- **왜 콜드스타트가 우선인가**: 새벽 00:00~05:59는 슬립을 허용하기로 했으므로
  (위 항목) 그 시간 첫 방문자는 30~60초를 기다린다. **가장 체감이 큰 항목이고,
  비용을 늘리지 않고 줄일 수 있는 유일한 항목이다.** `-Xms128m`을 넣었다 —
  ⚠️ `-Xms`를 주지 않으면 **초기 힙이 8MB**(컨테이너 메모리의 1/64)라, Spring
  기동이 그 안에서 힙 확장과 young GC를 수십 번 반복한다. 0.1 CPU에서는 그 낭비가
  그대로 대기 시간이 된다
- **`server.shutdown: graceful`은 이미 기본값이었다**: Spring Boot 3.5부터
  기본값이 `GRACEFUL`이다(바이트코드로 확인). **그래서 진짜 위험은 다른 데
  있었다** — `spring.lifecycle.timeout-per-shutdown-phase` 기본값이 **30초**이고
  Render의 SIGTERM→SIGKILL 여유도 약 30초다. 즉 기다리다 강제 종료될 수 있다.
  20초로 줄였다. `shutdown: graceful`은 기본값이어도 명시했다 — 버전이 올라가며
  조용히 바뀌면 **요청이 그냥 사라지는 방식으로** 깨진다
- **메모리는 `-Xmx`를 건드리지 않고 힙 밖을 줄였다**: Tomcat 스레드 200→20
  (스택이 스레드마다 붙는다) · SerialGC 고정(G1은 힙 밖 자료구조가 더 붙는다).
  ⚠️ **`-Xmx400m` + 힙 밖 약 180MB는 이미 512MB를 넘는다** — 힙이 정말 400MB까지
  차면 OOM으로 죽는다. 낮추자니 M4의 PDF→이미지 변환이 힙을 쓴다. **그래서
  낮추지 않고 감시 대상으로 올렸다**(`COST_GUARDRAILS.md §5`에 메모리 경고선 420MB)
- **채택하지 않은 것**: `spring.main.lazy-initialization`(기동은 빨라지지만 비용이
  **첫 요청**으로 옮겨간다 — 고치려는 게 바로 그 첫 요청이다) ·
  `-XX:TieredStopAtLevel=1`(기동 이득 대신 M4 PDF 변환 같은 CPU 작업이 느려진다) ·
  CDS/AOT(빌드 중 DB가 필요해 이미지 빌드가 깨질 수 있고, **Docker 데몬이 꺼져
  있어 검증 불가**) · 가상 스레드(동시성 상한이 사라져 512MB에서 위험) ·
  `ddl-auto: none`(기동 몇십 ms 아끼려고 스키마 드리프트 감지를 버리는 거래)
- **미확정 사항**: ⚠️ **효과 수치를 실측하지 못했다.** Docker 데몬이 꺼져 있어
  이미지 빌드·기동 시간·메모리를 다시 재지 못했다. 설정값은 Spring 바인딩까지
  검증했지만 **8.6초 → 몇 초가 되는지는 배포 후에 확인해야 한다**
- **구현**: `backend/Dockerfile`(JVM 옵션) · `application.yml`(BE 승인 대기 —
  `docs/backend/BACKEND_HANDOFF.md` 최상단) · `DataSourcePoolConfigTest`(신규) ·
  `docs/ops/COST_GUARDRAILS.md §3.2`·`§5`·`§6`·`§7` · `infra/render/README.md §4`

  · **비밀번호를 본인이 정한다** — 관리자가 정해 전달하고 나중에 바꾸게 하는 과정이 없다
  · **부트스트랩 경로가 운영에 영구히 남지 않는다**
- **탈락한 안**:
  · **A(Flyway V2 시드)** — BCrypt 해시가 **git 이력에 영구히** 남는다. Private
    저장소라도 "시크릿을 커밋하지 않는다"는 기존 원칙과 어긋난다
  · **B(콘솔 INSERT)** — 해시를 직접 만들어야 하고 **비밀번호를 관리자가 정하게**
    된다. D가 되는 상황에서 굳이 쓸 이유가 없다
  · **C(환경변수 부트스트랩)** — 코드가 늘고 Render 환경변수가 5개 → 8개가 되며,
    "부트스트랩 코드를 언제 지우나"라는 결정이 하나 더 생긴다
- **알아둘 것 2가지** (절차서에 반영했다):
  · 🔴 **`role`은 JWT 클레임이다** (`JwtProvider` — 요청마다 DB를 다시 읽지 않는다).
    UPDATE 후 **재로그인해야** PASTOR 토큰이 발급된다
  · 가입 폼이 **소속 마을을 필수로 요구한다**. 전도사는 마을 소속이 아닐 수 있는데
    폼이 강제하므로, 같은 UPDATE에서 `village = NULL`로 정리한다
- **이 절차는 초기 1회만이다**: `SPEC_API §8.4`가 **마지막 PASTOR 강등을
  `VALIDATION_ERROR`로 막는다**("아무도 회원을 승인할 수 없게 되는 것을 방지").
  즉 한 번 만들면 다시 0명이 될 수 없다. **스펙은 "0명이 되는 것"은 막았지만
  "처음부터 0명인 것"은 다루지 않았다** — 이 결정이 그 빈칸을 메운다

## 2026-08-26 — 백엔드 자동 배포: `develop` 머지 → GitHub Actions → Render

**결정**: 백엔드 담당자가 **push하고 머지만 하면 서버에 자동으로 올라가도록** 한다.
배포 트리거는 **`develop` 브랜치**, 트리거 주체는 **GitHub Actions**다.

- **왜 `main`이 아니라 `develop`인가**: 아직 공개 사용자가 없고 BE가 막 개발을
  시작했다. BE의 평소 흐름(`feat/be-*` → `backend_develop` → `develop`)에서 바로
  반영되는 편이 확인 주기가 짧다. `main`이면 배포할 때마다 `develop → main` PR을
  하나 더 머지해야 하는데 지금 단계에서 그 의식은 값을 하지 못한다.
  **`main`은 "공개된 것"이라는 의미를 유지하고, 공개 시점에 배포 대상을 옮긴다.**
- **왜 Jenkins가 아니라 Actions인가**: ⚠️ **Jenkins는 PM 로컬 PC에 있다.**
  PC가 꺼져 있으면 머지해도 배포가 일어나지 않고 나중에 PC를 켜야 반영된다.
  **자동 배포가 사람의 PC 상태에 달려 있으면 그건 자동이 아니다.**
  Jenkins는 CI 검증·파이프라인 학습 역할을 그대로 유지한다(변경 경로 감지·
  시크릿 스캔·병렬 검증은 Actions에 없다). Jenkins를 상시 가동 서버로 옮기면
  CD를 되가져올 수 있다
- **폐기되는 기존 설계**: `CICD.md §3.2`의 "Jenkins = CD" 역할 분담과
  `Jenkinsfile`의 `Deploy` 스테이지. **두 곳에서 트리거하면 같은 커밋이 두 번
  배포되므로** Jenkinsfile에서는 제거했다

## 2026-08-25 — 월례회 업로드: 전송 구간만 진짜 진행률을 보여준다

**결정**: 변환 진행률은 만들 수 없지만 **전송 구간은 진짜 값을 보여준다.**

- **왜 변환 진행률이 불가능한가**: `POST /api/meetings`는 요청 하나다.
  브라우저가 PDF를 보내고 → 서버가 변환을 다 끝내고 → 응답 하나가 온다.

  도달할 통로 자체가 없으므로, 화면에 `7 / 10`을 띄우려면 숫자를 지어내야

- **전송 구간은 다르다**: 브라우저가 얼마나 보냈는지 정확히 안다

- **미확정 사항**: 진짜 변환 진행률을 원하면 서버가 알려줄 통로(SSE 또는

- **구현**: `frontend/src/lib/api/real.ts`·`types.ts`·`mock.ts` ·

## 2026-08-24 — ⚠️ 배포 전 필수: mock 사진 자산을 운영 배포에서 제외해야 한다

**결정**: `frontend/public/photos/`·`frontend/public/bulletins/`의 mock 자산은
**첫 공개 배포 전에 운영 번들에서 제외해야 한다.** 지금은 색인만 막아둔
상태이고, 그것으로는 부족하다.

**문제**: `public/`은 Next가 **인증 없이 정적 서빙**한다. `robots.txt`가
`/my`를 막아도 사진 파일 자체는 `/photos/retreat-2026/view/p001.webp` 같은
경로로 누구나 받을 수 있다. 실제로 `NEXT_PUBLIC_USE_MOCK=0`으로 띄워도
200으로 응답하는 것을 확인했다. 여기에는 **얼굴이 식별되는 실제 인물 사진
47장**이 들어 있다 — 회원 사진을 로그인 뒤에 두기로 한 결정(위 초상권 항목)이

- **영역**: 프론트엔드 자산 + 배포 설정
- **지금 해둔 것 (부분 방어)**
  - `robots.ts`에 `/photos`·`/bulletins` disallow 추가
  - `next.config.ts`에 해당 경로 `X-Robots-Tag: noindex, nofollow` 추가
  - ⚠️ **둘 다 "검색에 안 뜨게" 하는 것일 뿐, URL을 아는 사람의 직접 접근은
    막지 못한다.** robots는 크롤러에게 부탁하는 규약이다
- **왜 지금 당장 위험하지는 않은가**: 아직 배포된 환경이 없고(M1 배포는 BE
  미착수로 진행 안 됨) 저장소는 Private이다. **배포 시점에 반드시 처리해야
  하는 항목**으로 남긴다
- **실제 해결 방향** (배포 담당이 택일 — PM 확인 필요)
  1. **자산을 `public/`에서 빼고 mock 전용 라우트로 서빙** — `mock=1`일 때만
     응답하는 route handler를 두면 운영 빌드에서는 404가 된다. FE 코드는
     mock 응답의 URL을 그대로 쓰므로 경로 변경 영향이 작다
  2. **배포 파이프라인에서 해당 디렉터리 제외** — 플랫폼 설정이나 빌드 전
     삭제 단계. 간단하지만 잊기 쉽다
  3. **사진을 저장소에서 아예 제거**하고 개발자가 각자 받아오게 한다 — 가장
     안전하지만 M3 개발 편의를 잃는다
  - 실서비스는 사진을 **R2 presigned URL(만료됨)**로 서빙하므로, 운영에서 이
    자산이 필요하지 않다는 점은 확실하다
- **미확정 사항**: 위 3안 중 무엇을 택할지. **첫 공개 배포 전에 결정·적용 필요**
