# PM 결정 기록

PM(프론트엔드·인프라·기획 총괄)이 대화 중 구두로 전달한 스펙 결정·변경사항을
모아두는 로그다. **여기 있는 항목은 PM이 별도로 다시 요청하지 않아도, 결정이
나올 때마다 자동으로 추가된다** (`frontend/docs/HARNESS.md` §1 규칙).

목적: 백엔드 담당자를 포함해 이 대화에 없었던 사람도, 왜 화면/기능이 이렇게
바뀌었는지 나중에 추적할 수 있게 한다. `docs/SPEC_FUNCTIONAL.md`/
`docs/WIREFRAME.md`의 확정 스펙과는 별개로, **아직 그 문서에 반영되지 않은
최신 결정**을 여기서 먼저 확인할 수 있다.

형식: 최신 항목이 위에 온다.

## 2026-08-24 — 기능 브랜치는 머지 직후 삭제하고, 다시 손볼 땐 새로 판다 (재확인)

**결정**: `develop`(또는 `*_develop`) 아래에 **하위 브랜치를 파서 기능 작업**을 하고,
**테스트를 통과해 머지하면 그 브랜치를 로컬·원격 양쪽에서 즉시 삭제**한다. 그 기능을
다시 수정할 일이 생기면 **브랜치를 새로 판다** — 지웠던 브랜치를 되살리지 않는다.

- **영역**: 전체 (Git 운영)
- **근거**: 브랜치를 남겨두면 "이게 머지된 건지 아닌지"를 매번 이력으로 확인해야
  한다. 오늘 실제로 그 비용이 발생했다 — 이름이 같은 `origin/feat/fe-photo-upload`가
  남아 있어서, 내용이 이미 `frontend_develop`에 들어간 것인지 아닌지 확인하는 데
  시간이 들었다 (확인 결과 같은 내용이었고 삭제했다)
- **살아있는 브랜치 = 진행 중인 작업**이라는 규칙이 서면, 브랜치 목록 자체가
  현재 작업 현황이 된다
- **예외**: `main` · `develop` · `frontend_develop` · `backend_develop` ·
  `server_develop` 5개는 영구 브랜치다. 삭제하지 않는다
- **삭제 절차와 안전장치는 이미 `INTEGRATION.md §6.7`에 있다** (병합 확인 →
  `git branch -d` → 원격 삭제). GitHub의 "Automatically delete head branches"는
  계속 **끈 상태**로 둔다 — 영구 브랜치가 PR head일 때 함께 삭제된 사고가 있었다
- 이 결정은 2026-08-24에 처음 기록됐고, 오늘 PM이 **"수정 사항이 생기면 다시
  브랜치를 판다"** 는 조항을 덧붙여 재확인했다

## 2026-08-24 — ⚠️ 월례회 화면 문구를 와이어프레임 원문에서 바꿨다 (PM 확인 필요)

**결정**: `WIREFRAME.md §14b-2`의 **"저장·캡처 없이 열람만 가능합니다"를 쓰지
않았다.** 사실이 아니기 때문이다. 대신 이렇게 적었다:

> 다운로드 파일은 제공되지 않지만 **화면 캡처를 기술적으로 막을 방법은 없습니다.**
> 이 페이지에는 김OO 5678, 열람 시각이 함께 인쇄되어 있습니다.

- **영역**: 프론트엔드 (월례회 뷰어 문구)
- **근거**: `WORKPLAN.md §10`에 이미 "캡처 완전 차단은 불가능, 기간제한+워터마크로
  대응"이 기록돼 있다. `ARCHITECTURE.md §7.7`은 더 강하게 말한다 — **"막았다고
  믿고 더 민감한 자료를 올리는 것이 가장 위험하다."** 화면이 "캡처를 막았다"고
  말하면 그 위험을 우리가 직접 만드는 셈이다
- **CSS 오버레이 워터마크는 만들지 않았다**: 개발자도구로 두 번 클릭하면
  지워진다. **보호가 아니라 착각을 만드는 장치**다. 실제 워터마크는 서버가
  픽셀에 합성한다 (`SPEC_API §7.3` 처리 순서 4)
- **실제 억제력은 "당신 이름이 인쇄되어 있다"를 알려주는 것**이다. 우클릭 차단
  같은 연출보다 이게 낫다고 판단했다
- **이 기능이 막지 못하는 것** (화면에도, 코드 주석에도 명시):
  - 스크린샷·화면녹화 — 브라우저에 막을 API가 없다
  - 다른 기기로 화면 촬영 — 어떤 방법으로도 불가능
  - 이미 로드된 페이지 이미지는 브라우저 안에 있다. 열람 중 기간이 끝나면 다음
    페이지부터 막히지만 화면에 떠 있는 것은 되돌릴 수 없다
  - **실질 통제는 셋뿐**: 서버의 기간 검사 · 파일 URL 미발급(서버 스트리밍) ·
    서버 워터마크 burn-in. **앞의 둘은 전부 백엔드 몫이고 프론트는 아무것도
    보증하지 않는다**
- **미확정 사항**: **문구 변경을 PM이 승인할지.** 원문대로 돌리고 싶으면
  알려주면 되돌린다 — 다만 그러면 화면이 사실과 다른 말을 하게 된다
- **구현**: `frontend/src/app/my/meetings/[id]/_components/MeetingViewer.tsx`

## 2026-08-24 — 월례회·삭제 화면에서 정한 것들

**결정**: 스펙에 없어 구현자가 정한 사항들. 다르게 원하면 바꾼다.

- **영역**: 프론트엔드만

**월례회**
- **목록에서도 임원에게 `임원 열람` 배지 + 열람 버튼을 노출한다** (와이어프레임은
  뷰어에만 명시). 근거: `SPEC_API §7.1` "`L` 이상은 status 무관". 목록에서
  버튼이 없으면 임원이 종료된 자료를 열 방법이 없다
- **CLOSED 카드의 "임원에게 문의해 주세요"는 일반 회원에게만 보인다** (임원에게는
  자기가 열 수 있으므로 의미 없는 문구다)
- **`meetings.get`을 캐시하지 않는다** (`staleTime:0 / gcTime:0`) — 뒤로 갔다
  오면 "아직 볼 수 있다"는 낡은 응답이 남는다
- **문서 제목을 `generateMetadata`에 넣지 않는다**: 서버에서는 권한 `M`이라 항상
  실패하고, 문서 제목이 탭·브라우저 히스토리에 남는 것도 이 기능 취지와 맞지 않다
- **열람 불가를 두 경로 모두 처리했다** (`200 + canView:false` / `403`) — 스펙이
  양쪽을 암시해서다 (`BACKEND_HANDOFF.md` 확정 요청 참고)

**사진·앨범 삭제**
- **배치**: 앨범 삭제는 목록 카드가 아니라 **앨범 상세 하단 위험 구역**, 사진
  삭제는 **라이트박스 `⋮` 메뉴** 안. 스크롤되는 그리드의 썸네일 옆 삭제 버튼은
  만들지 않는다 — 오터치 한 번이 47장이다
- **확인 강도를 비대칭으로 뒀다**: 앨범 = **제목 타이핑 + `confirm()`**
  (47장, 피해가 눈에 보이지 않음) · 사진 1장 = 3탭 + 취소 초기 포커스
  (1장, 눈앞에 보임). `confirm()`은 "클릭했다"만 증명하지만 제목 타이핑은
  **어느 앨범에 있는지 읽었다**를 증명한다
- **대량 삭제를 제공하지 않는다**: `§6.9`에 bulk 엔드포인트가 없어 N번 순차
  요청이 되고 "일부만 지워진" 상태가 생긴다. 비가역 동작에서 그 상태를 만들 수
  있게 하지 않는다. 삭제는 **ZIP 다운로드 선택 모드와 완전히 분리** — 하단 바
  오터치가 30장 다운로드가 아니라 30장 삭제가 되면 안 된다
- **낙관적 제거를 하지 않는다**: mock은 정적 파일이라 지워지지 않는데, 숨기면
  새로고침에 되살아나 "삭제가 고장났다"로 읽힌다. mock 모드에서만 안내 문장을
  붙였고 `=0` 번들에서 제거되는 것을 확인했다

**주보 다운로드**
- **"현재 보고 있는 장"만 받는다**: `WIREFRAME §12`에 장 수와 무관하게 버튼이
  하나뿐이고 페이저 바로 아래에 있다. 장별 버튼 나열이나 전체 ZIP은 와이어프레임에
  없어서 만들지 않았다. `FR-BUL-04`의 "장별 개별"은 장을 넘겨 각각 받는 것으로
  충족한다. 1장짜리 주보에서는 문구를 "다운로드"로 바꿔 선택지가 있는 것처럼
  읽히지 않게 한다

- **미확정 사항**: 없음
- **구현**: `frontend/src/app/my/meetings/**`,
  `frontend/src/app/my/photos/[id]/_components/{AlbumDangerZone,PhotoDeletePanel}.tsx`,
  `frontend/src/app/my/bulletin/_components/BulletinViewer.tsx`

## 2026-08-24 — ⚠️ 브랜드 색 대비가 WCAG 기준에 미달한다 (PM 결정 필요)

**결정 필요**: 접근성 감사에서 **초록 CTA와 랜딩 히어로 텍스트가 대비 기준을
못 넘긴다**는 것이 실측으로 확인됐다. 브랜드 색은 PM이 정한 것이라
(위 "디자인 톤: 베이지 + 그린" 항목) 임의로 바꾸지 않고 숫자와 선택지만 남긴다.

- **영역**: 프론트엔드 디자인 토큰. 결정하면 전 화면에 영향
- **측정값** (실제 Chromium에서 합성된 픽셀 기준, 22라우트 × 360/1440px)
  | 대상 | 측정 | 기준 |
  |---|---|---|
  | 초록 CTA `#3e8e5b` + 네이비 텍스트 | **3.85:1** | 4.5:1 |
  | 초록 CTA `#3e8e5b` + 흰 텍스트 | **4.02:1** | 4.5:1 |
  | 랜딩 히어로 아크로스틱(초록) | **1.71~2.95:1** | 4.5:1 (큰 글자 3:1도 미달) |
  | `--color-red-500 #e5484d` 경고문 | 3.06~3.91:1 | 4.5:1 |
- **초록이 특히 곤란한 이유**: **중간 명도라서 네이비도 흰색도 4.5:1을 못
  넘긴다.** 텍스트 색만 바꿔서는 해결되지 않고 초록 자체를 옮겨야 한다
  - 네이비 텍스트 유지 → 초록을 `≈#4FA96F` 이상으로 **밝게** (5.34:1)
  - 흰 텍스트로 전환 → 초록을 `≈#35794E` 이하로 **어둡게** (5.25:1)
  - 영향 범위: 헤더 "처음이신가요" 알약 + 모든 primary 버튼
- **랜딩 히어로**: 코드 주석은 70% 스크림이 대비를 유지한다고 적혀 있었지만
  **사실이 아니었다** (실측 1.71:1). 선택지: ① 글자를 흰색으로(5.84:1)
  ② 스크림을 훨씬 강하게 ③ 워드마크로 보고 WCAG 로고타입 면제 주장
  (해당 블록은 `aria-hidden`이라 이 주장이 가능하다)
- **`--color-red-500`**: 이 토큰이 **전경색과 배경색 양쪽으로** 쓰여서 한쪽을
  어둡게 하면 다른 쪽이 깨진다. `--color-danger-text`/`--color-danger-surface`
  분리가 필요하다
- **다크 스킴은 절반만 구현돼 있다**: `globals.css`가 `--background`/
  `--foreground`만 뒤집고 나머지 6토큰은 고정이다. 그래서 다크에서만 나는
  실패 4건이 있다 (`/worship` **1.06:1** 등). 전부 기존 문제이고 덮어 가리지
  않았다
- **미확정 사항**: 위 3가지 전부. **결정 전까지 axe `color-contrast` 위반
  35노드가 남아 있다** (감사 전 283노드에서 줄어든 값)
- **구현**: 없음 — 측정만 함

## 2026-08-24 — PWA 캐싱 정책: `/_next/image`를 전면 제외한다

**결정**: 서비스워커 캐시 허용 목록에서 **`/_next/image`를 통째로 제외**한다.
`/_next/static/`만 허용한다.

**이유**: 회원 앨범 커버가 `next/image`를 타서 실제 요청 URL이
`/_next/image?url=%2Fphotos%2Fretreat-2026%2Fthumb%2Fp001.webp`가 된다.
**경로가 `/_next/`로 시작해 정적 자산처럼 보이지만 내용은 얼굴이 식별되는
회원 사진이다.** `/_next/`를 통째로 허용하면 로그아웃하거나 기기를 공유한
뒤에도 캐시에서 남의 얼굴을 꺼낼 수 있다.

- **영역**: 프론트엔드 (`frontend/public/sw.js`)
- **대가**: **공개 페이지가 오프라인에서 이미지 없이 렌더된다.**
  `SPEC_NONFUNCTIONAL.md §14`("보안 우선")가 요구하는 트레이드오프로 판단했다
- **서비스워커는 화이트리스트다** (블랙리스트가 아니다) — 앞으로 새 라우트가
  추가돼도 조용히 캐시되지 않는다. 민감 경로 목록은 `robots.ts`의 disallow

- **2차 방어**: 로그아웃 시 `CLEAR_CACHES`로 캐시를 비운다
- **검증**: 회원 페이지 6개를 순회한 뒤 캐시 전량 덤프 — 27개 항목, 위반 0건

## 2026-08-24 — PWA에 의존성을 추가하지 않았다 (Serwist 미사용)

**결정**: `ARCHITECTURE.md §2.1`이 언급한 Serwist를 쓰지 않고 자체 서비스워커를

## 2026-08-24 — 기능 완료된 `feat/fe-*` 브랜치는 머지 후 삭제한다

**결정**: `feat/fe-*` 작업 브랜치는 기능 작업이 끝나고 상위 브랜치
(`frontend_develop`)에 머지되면 **로컬과 GitHub 양쪽에서 삭제**한다.
브랜치 목록에 완료된 작업이 계속 쌓이면 지금 진행 중인 작업이 무엇인지
한눈에 안 보인다.

- **영역**: 협업·Git 운영 규칙 (프론트엔드 브랜치에 한정)
- **스펙 문서 반영 상태**: ✅ `docs/INTEGRATION.md` §6.7에 정식 반영 완료.
  기존 §6.7에도 "머지된 `feat/*`는 삭제한다"는 규칙 자체는 있었지만, **삭제
  절차가 없었고 "GitHub 자동 삭제 옵션 켜두기"라는 틀린 지시가 함께 있었다**
  (아래 "연관 주의사항" 참고). §6.7과 §2.3 체크리스트를 같이 고쳤다
- **삭제 전 확인 절차** (이번에 실제로 적용한 순서):
  1. 해당 브랜치가 상위 브랜치에 **완전히 병합됐는지** `git merge-base
     --is-ancestor`로 검증한다
  2. 로컬은 `git branch -d`(안전 삭제)를 쓴다 — 미병합이면 git이 거부하므로
     실수 방지가 된다. `-D`(강제)는 고유 커밋이 0개임을 따로 확인한
     경우에만 쓴다
  3. 원격은 `git push origin --delete`로 지운다
- **적용 범위 주의**: `feat/infra-*`는 서버·인프라 담당 영역이므로 FE가
  임의로 지우지 않는다. `main`·`develop`·`*_develop`은 영구 브랜치로 삭제
  대상이 아니다
- **연관 주의사항**: GitHub 저장소 설정 "Automatically delete head branches"는
  **계속 꺼둔다.** `frontend_develop` 같은 영구 브랜치가 PR head가 될 때
  자동 삭제되는 사고가 이전에 실제로 발생했다 (`docs/CICD.md` §4 관련)
- **미확정 사항**: 없음
- **구현**: 2026-08-24 M1·M2 완료 시점에 `feat/fe-*` 19개 삭제
  (`feat/fe-auth-core`, `feat/fe-signup-followup`, `feat/fe-password-reset`,
  `feat/fe-my-home`, `feat/fe-internal-notices`, `feat/fe-my-profile` +
  M1 시절 13개)
