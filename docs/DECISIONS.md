# PM 결정 기록

PM(프론트엔드·인프라·기획 총괄)이 대화 중 구두로 전달한 스펙 결정·변경사항을
모아두는 로그다. **여기 있는 항목은 PM이 별도로 다시 요청하지 않아도, 결정이
나올 때마다 자동으로 추가된다** (`frontend/docs/HARNESS.md` §1 규칙).

목적: 백엔드 담당자를 포함해 이 대화에 없었던 사람도, 왜 화면/기능이 이렇게
바뀌었는지 나중에 추적할 수 있게 한다. `docs/SPEC_FUNCTIONAL.md`/
`docs/WIREFRAME.md`의 확정 스펙과는 별개로, **아직 그 문서에 반영되지 않은
최신 결정**을 여기서 먼저 확인할 수 있다.

형식: 최신 항목이 위에 온다.

## 2026-08-24 — ⚠️ 배포 전 필수: mock 사진 자산을 운영 배포에서 제외해야 한다

**결정**: `frontend/public/photos/`·`frontend/public/bulletins/`의 mock 자산은
**첫 공개 배포 전에 운영 번들에서 제외해야 한다.** 지금은 색인만 막아둔
상태이고, 그것으로는 부족하다.

**문제**: `public/`은 Next가 **인증 없이 정적 서빙**한다. `robots.txt`가
`/my`를 막아도 사진 파일 자체는 `/photos/retreat-2026/view/p001.webp` 같은
경로로 누구나 받을 수 있다. 실제로 `NEXT_PUBLIC_USE_MOCK=0`으로 띄워도
200으로 응답하는 것을 확인했다. 여기에는 **얼굴이 식별되는 실제 인물 사진
47장**이 들어 있다 — 회원 사진을 로그인 뒤에 두기로 한 결정(위 초상권 항목)이
이 경로로 우회된다.

- **영역**: 프론트엔드 자산 + 배포 설정
- **지금 해둔 것 (부분 방어)**
  - `robots.ts`에 `/photos`·`/bulletins` disallow 추가
  - `next.config.ts`에 해당 경로 `X-Robots-Tag: noindex, nofollow` 추가
  - ⚠️ **둘 다 "검색에 안 뜨게" 하는 것일 뿐, URL을 아는 사람의 직접 접근은
    막지 못한다.** robots는 크롤러에게 부탁하는 규약이다
- **왜 지금 당장 위험하지는 않은가**: 아직 배포된 환경이 없고(M1 배포는 BE
  미착수로 진행 안 됨) 저장소는 Private이다. **배포 시점에 반드시 처리해야
  하는 항목**으로 남긴다
- **실제 해결 방향** (배포 담당이 택일 — PM 확인 필요)
  1. **자산을 `public/`에서 빼고 mock 전용 라우트로 서빙** — `mock=1`일 때만
     응답하는 route handler를 두면 운영 빌드에서는 404가 된다. FE 코드는
     mock 응답의 URL을 그대로 쓰므로 경로 변경 영향이 작다
  2. **배포 파이프라인에서 해당 디렉터리 제외** — 플랫폼 설정이나 빌드 전
     삭제 단계. 간단하지만 잊기 쉽다
  3. **사진을 저장소에서 아예 제거**하고 개발자가 각자 받아오게 한다 — 가장
     안전하지만 M3 개발 편의를 잃는다
  - 실서비스는 사진을 **R2 presigned URL(만료됨)**로 서빙하므로, 운영에서 이
    자산이 필요하지 않다는 점은 확실하다
- **미확정 사항**: 위 3안 중 무엇을 택할지. **첫 공개 배포 전에 결정·적용 필요**
- **구현**: `frontend/src/app/robots.ts`, `frontend/next.config.ts` (부분 방어만)

## 2026-08-24 — M3 사진첩 화면 구현 시 정한 것들

**결정**: 앨범 목록·사진 그리드·라이트박스를 만들면서 스펙에 없어 구현자가
정한 사항들이다. 다르게 원하면 알려주면 바꾼다.

- **영역**: 프론트엔드만
- **정한 것**
  - **그리드 열 수**: 와이어프레임의 모바일 3열은 유지하고, `sm`/`md`/`lg`에서
    4/5/6열로 늘린다. 데스크톱에서 3열이면 썸네일이 과하게 커진다
  - **라이트박스 위치 표시 분모는 "앨범 전체 장수"** (`35 / 47`)다. 무한
    스크롤로 로드된 장수가 아니다 — 로드된 수를 쓰면 스크롤할수록 분모가
    커져서 사용자가 전체 규모를 알 수 없다
  - **핀치 줌은 구현하지 않았다.** 와이어프레임 §13-4에 있지만, 반쯤 동작하는
    커스텀 제스처 핸들러를 넣는 대신 `user-scalable=no`를 걸지 않아 **브라우저
    기본 핀치(전체 페이지 확대)가 살아있는 상태**로 뒀다. 사진 전용 줌·팬은
    별도 작업 단위로 남긴다
  - **회원 전용 페이지는 서버 prefetch를 하지 않는다.** 세션이 필요한 데이터를
    빌드 시점에 가져올 수 없고, 성공한다면 특정 사용자 데이터가 정적 HTML에
    구워지기 때문이다. 공개 페이지(`/news`)와 의도적으로 다른 패턴이다
  - **사진 목록에 `next/image`를 쓰지 않았다** (`<img>` + eslint-disable).
    실서비스 URL이 만료되는 R2 presigned URL이라 옵티마이저가 매번 캐시
    미스가 나고, thumb은 이미 640px WebP로 서버에서 만들어둔다
- **미확정 사항 (PM 확인 필요)**
  - 라이트박스 핀치 줌을 정식으로 구현할지, 브라우저 기본 동작으로 둘지
  - 사진 다운로드(`SPEC_API §6.7`)·선택 모드 ZIP(`§13-3`)은 아직 미구현
- **구현**: `frontend/src/app/my/photos/**`

## 2026-08-24 — 수련회 실사진: 공개 페이지에는 얼굴 비식별 3장만 쓴다

**결정**: PM이 수련회 사진이 담긴 Google Drive 폴더를 전달했다(2026-08-19).
47장을 내려받아 WebP로 최적화했고(277MB → 7.2MB, EXIF 메타데이터 제거),
**공개 페이지에는 얼굴이 식별되지 않는 예배 장면 사진만 쓴다. 나머지는 전부
로그인 뒤 회원 전용 사진첩 자산으로만 둔다 — 초상권 때문이다.**

공개 사이트는 검색엔진에 색인되므로, 약 40명의 얼굴이 그대로 드러나는
사진이 공개 페이지에 올라가면 당사자 동의 없이 무기한 공개되는 것과 같다.
회원 사진을 로그인 뒤에 두는 원칙은 `docs/PLAN.md` §4.7에 이미 있다.

- **영역**: 프론트엔드(공개 페이지 이미지) + 자산 관리 정책. 백엔드 영향은
  사진첩 API 계약뿐이다 (`docs/SPEC_API.md` §6, 별건으로 이미 반영)
- **공개 허용 3장** (`frontend/public/images/`) — 실루엣·뒷모습·군중이라
  개인 식별이 안 되는 것만 골랐다:
  - `worship-hero.webp` (1920×1080) — 어두운 예배 장면, 손 든 실루엣.
    어두운 영역이 많아 텍스트/로고 오버레이에 적합
  - `worship-wide.webp` (1920×1080) — 스크린을 향해 손 든 찬양 장면
  - `gathering.webp` (1600×900) — 예배실에 모여 있는 공동체 (밝은 톤)
- **회원 전용**: `frontend/public/photos/retreat-2026/` 47장. **공개 페이지
  (`/`, `/home`, `/welcome`, `/worship`, `/about`, `/location`, `/news`)에
  절대 쓰지 않는다.** 크롭·확대로 특정 인물이 식별되게 만드는 것도 금지 —
  그래서 3장 모두 원본 비율(16:9) 그대로 노출한다
- **스펙 문서 반영 상태**: `docs/WIREFRAME.md` §1의 "실사진 확보 전까지 Hero는
  단색 + 워드마크" 서술은 이 결정으로 대체된다 — 아직 문서 갱신 전이고
  실제 코드가 최신 기준. `docs/PLAN.md` §4.7의 회원 사진 비공개 원칙과는
  충돌 없이 일관된다
- **미확정 사항**:
  1. **사진에 찍힌 분들이 이 제한적 공개 사용에도 동의했는지 PM 확인 필요.**
     얼굴 비식별이라고 판단해 고른 것은 FE 판단이며, 촬영 당시 "공개
     홈페이지 게시"까지 동의를 받았는지는 확인되지 않았다. 동의 근거가
     없으면 공개 페이지에서도 내리고 단색 배경으로 되돌린다
  2. **드림센터 외관·입구 사진이 여전히 없다.** `/welcome`·`/location`의 해당
     placeholder는 그 건물을 찍은 실사진이어야 하므로(기존 PM 결정) 수련회
     사진으로 대체할 수 없다 — placeholder와 ❓ 표기를 그대로 남겨뒀다
  3. `/home` "최근 말씀" 썸네일은 설교 영상 썸네일이라 사진 교체 대상이
     아니다 — 영상 연동 시 채워진다
- **구현**: `frontend/src/app/_components/LandingGate.tsx`(배경, 장식이므로
  `alt=""` + 스크림), `frontend/src/app/home/page.tsx`(Hero / "우리는" /
  "함께한 순간들" 3곳). Next 16에서 `priority`가 deprecated되어
  above-the-fold는 `loading="eager"` + `fetchPriority="high"`, 나머지는
  lazy로 뒀다 (Lighthouse 90+ 예산, `docs/WORKPLAN.md` 품질 게이트)

## 2026-08-24 — 기능 완료된 `feat/fe-*` 브랜치는 머지 후 삭제한다

**결정**: `feat/fe-*` 작업 브랜치는 기능 작업이 끝나고 상위 브랜치
(`frontend_develop`)에 머지되면 **로컬과 GitHub 양쪽에서 삭제**한다.
브랜치 목록에 완료된 작업이 계속 쌓이면 지금 진행 중인 작업이 무엇인지
한눈에 안 보인다.

- **영역**: 협업·Git 운영 규칙 (프론트엔드 브랜치에 한정)
- **스펙 문서 반영 상태**: ✅ `docs/INTEGRATION.md` §6.7에 정식 반영 완료.
  기존 §6.7에도 "머지된 `feat/*`는 삭제한다"는 규칙 자체는 있었지만, **삭제
  절차가 없었고 "GitHub 자동 삭제 옵션 켜두기"라는 틀린 지시가 함께 있었다**
  (아래 "연관 주의사항" 참고). §6.7과 §2.3 체크리스트를 같이 고쳤다
- **삭제 전 확인 절차** (이번에 실제로 적용한 순서):
  1. 해당 브랜치가 상위 브랜치에 **완전히 병합됐는지** `git merge-base
     --is-ancestor`로 검증한다
  2. 로컬은 `git branch -d`(안전 삭제)를 쓴다 — 미병합이면 git이 거부하므로
     실수 방지가 된다. `-D`(강제)는 고유 커밋이 0개임을 따로 확인한
     경우에만 쓴다
  3. 원격은 `git push origin --delete`로 지운다
- **적용 범위 주의**: `feat/infra-*`는 서버·인프라 담당 영역이므로 FE가
  임의로 지우지 않는다. `main`·`develop`·`*_develop`은 영구 브랜치로 삭제
  대상이 아니다
- **연관 주의사항**: GitHub 저장소 설정 "Automatically delete head branches"는
  **계속 꺼둔다.** `frontend_develop` 같은 영구 브랜치가 PR head가 될 때
  자동 삭제되는 사고가 이전에 실제로 발생했다 (`docs/CICD.md` §4 관련)
- **미확정 사항**: 없음
- **구현**: 2026-08-24 M1·M2 완료 시점에 `feat/fe-*` 19개 삭제
  (`feat/fe-auth-core`, `feat/fe-signup-followup`, `feat/fe-password-reset`,
  `feat/fe-my-home`, `feat/fe-internal-notices`, `feat/fe-my-profile` +
  M1 시절 13개)

## 2026-08-21 — 첫 화면 클릭 게이트: 신규/기존 방문자 분기

**결정**: `/`(루트)의 동작을 바꾼다. 기존에는 스플래시를 탭하면 사라지고

  실제 로그인 기능은 이후 작업)

기존 스크롤형 HOME 콘텐츠는 삭제하지 않고 **`/home` 경로로 그대로 이동**한다
(PM 확인: "스크롤 콘텐츠는 그대로 두고 새 경로로 이동").

- **영역**: 프론트엔드만. 백엔드 영향 없음 (로그인 기능 자체는 아직 미구현)
- **스펙 문서 반영 상태**: `docs/WIREFRAME.md` §1(HOME)·이전 결정(아래 "홈 진입
