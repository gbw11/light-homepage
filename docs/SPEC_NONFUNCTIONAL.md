```
NFR-<범주>-<번호>
  PERF 성능       AVAIL 가용성      SEC  보안
  PRIV 개인정보    COMP  호환성      A11Y 접근성

  SCALE 확장성     OPS   운영·모니터링   LEGAL 법·규정
```

각 항목에는 **측정 방법**이 있습니다. 측정할 수 없는 요구는 요구가 아니라 희망입니다.

### 0.1 이 프로젝트의 비기능 우선순위
일반적인 서비스와 다릅니다. **비용과 보안이 성능보다 우선**합니다.

| 순위 | 범주 | 이유 |
|---|---|---|
| 1 | **보안·개인정보** | 예산안·회의록·월례회·회원 개인정보를 다룬다. 유출은 되돌릴 수 없다 |
| 2 | **비용** | $0가 제약이다. 초과하면 서비스를 유지할 수 없다 |
| 3 | **가용성(공개 영역)** | 전도 목적. 검색으로 들어온 사람이 못 보면 존재 의미가 없다 |
| 4 | 성능 | 모바일 90%. 느리면 이탈한다 |
| 5 | 유지보수 | 2인 부업 프로젝트. 방치가 최대 실패 요인 |

### 1.3 전송량 제약 (비용과 직결)
| ID | 항목 | 목표 | 근거 |
|---|---|---|---|
| NFR-PERF-12 | 앨범 200장 열람 시 전송량 | **< 20MB** | 썸네일 640px(~80KB) × 200 = 16MB |
| NFR-PERF-13 | 사진 원본 1장 | ~1.2MB | 2560px q85 WebP |
| NFR-PERF-14 | 공개 홈 첫 로드 | < 1.5MB | Hero 이미지 포함 |

### 1.4 구현 제약
- 사진 그리드는 **페이지네이션 또는 커서 기반 무한 스크롤**. 200장을 동시에 DOM에 올리지 않는다
- Hero 이미지만 `priority`, 나머지는 `loading="lazy"`
- 모든 이미지에 명시적 `width`/`height` → CLS 방지
- 리치텍스트 에디터(Tiptap)는 **동적 import** — 작성 화면에서만 로드
- 회원 영역 첫 진입 시 백엔드 웨이크업 가능 → **로딩 상태를 반드시 표시**(빈 화면 금지)

## 2. 가용성 (NFR-AVAIL)

### 2.1 목표
| ID | 대상 | 목표 | 비고 |
|---|---|---|---|
| NFR-AVAIL-01 | **공개 영역** | **99.9%** | Vercel 정적 호스팅. 백엔드와 무관 |
| NFR-AVAIL-02 | 회원 영역 | 95% | 무료 호스팅 제약을 감안한 현실적 목표 |
| NFR-AVAIL-03 | 백엔드 콜드스타트 | 첫 요청 < 60s | Render 무료. 핑으로 완화 |

### 2.2 ★ 핵심 설계 원칙
> **공개 영역은 백엔드에 의존하지 않는다.**

Render 무료 인스턴스는 15분 유휴 시 슬립되고 JVM 콜드스타트가 30~60초입니다. 공개 페이지를 정적(SSG)으로 만들어 **백엔드가 슬립이거나 장애여도 전도용 사이트는 정상 동작**하게 합니다.

이 설계 덕분에 무료 인프라의 가장 큰 약점이 **회원 영역 첫 진입 지연**으로만 국한됩니다.

### 2.3 완화 조치
| ID | 조치 | 상세 |
|---|---|---|
| NFR-AVAIL-04 | 헬스체크 핑 | `cron-job.org`로 10분마다 `/actuator/health` → 슬립 방지 |
| NFR-AVAIL-05 | 공개 공지 정적화 | 빌드 시점에 가져와 정적 생성 → 방문자 트래픽이 백엔드를 깨우지 않음 |

| NFR-AVAIL-07 | 장애 시 안내 | 백엔드 응답 실패 시 "잠시 후 다시 시도" + 연락처 |

## 3. 보안 (NFR-SEC) — 최우선

### 3.1 인증
| ID | 요구 | 검증 |
|---|---|---|
| NFR-SEC-01 | 비밀번호는 **BCrypt** 해싱 저장 (평문·단순 해시 금지) | DB 확인 |
| NFR-SEC-02 | JWT는 `HttpOnly; Secure; SameSite=Lax` **쿠키로만** 전달 | 브라우저 개발자도구 |
| NFR-SEC-03 | localStorage·sessionStorage에 토큰 저장 금지 | 코드 검색 |
| NFR-SEC-04 | 액세스 토큰 30분 / 리프레시 14일 | 설정 확인 |
| NFR-SEC-05 | 리프레시 토큰은 DB에 **해시**로 저장, 로그아웃 시 폐기 | DB 확인 |
| NFR-SEC-06 | 만료·위조·다른 서명키 JWT → `401` | 테스트 |
| NFR-SEC-07 | `JWT_SECRET`은 최소 256bit 랜덤 | 설정 확인 |
| NFR-SEC-08 | 비밀번호 재설정 링크는 1회용·만료 | 테스트 |

### 3.2 ★ 인가 — RLS 상실의 보완
초기 설계(Supabase + RLS)에서는 코드에서 권한 검사를 빠뜨려도 **DB가 막아줬습니다.** Spring이 단일 DB 계정으로 접속하는 현재 구조에서는 **그 방어선이 없습니다.**

| ID | 요구 | 검증 |
|---|---|---|
| NFR-SEC-09 | **인가 테스트 매트릭스 전항 통과** (역할 × 엔드포인트) | 자동 테스트 (CI 필수) |
| NFR-SEC-10 | 모든 보호 엔드포인트에 `@PreAuthorize` | 코드 리뷰 |
| NFR-SEC-11 | Service 계층에서 리소스 분류·소유 **재검사** | 코드 리뷰 |
| NFR-SEC-12 | 권한 없는 리소스는 **404** (존재 자체를 숨김) | 테스트 |
| NFR-SEC-13 | 게시물 상세 조회는 **id로 찾고 그 글의 분류 권한 확인** (분류 파라미터 필터링 금지) | 코드 리뷰 |
| NFR-SEC-14 | 마지막 `PASTOR` 강등·탈퇴 거부 | 테스트 |

> **NFR-SEC-09가 이 프로젝트의 마지막 방어선입니다.** 권한 회귀를 사람의 기억으로 막을 수는 없으므로, CI에서 반드시 실행되어야 합니다.

### 3.3 파일 접근
| ID | 요구 | 검증 |
|---|---|---|
| NFR-SEC-15 | R2 버킷은 **완전 비공개**. 공개 URL 없음 | 버킷 설정 |
| NFR-SEC-16 | 파일 접근은 **presigned URL(10분)** 로만 | 코드 리뷰 |
| NFR-SEC-17 | 로그아웃 상태에서 첨부·사진 URL 접근 → 거부 | 테스트 |
| NFR-SEC-18 | **월례회는 presigned URL 미발급** — 서버가 직접 스트리밍 | 네트워크 탭 확인 |
| NFR-SEC-19 | 월례회 응답에 R2 키가 포함되지 않음 | 네트워크 탭 확인 |
| NFR-SEC-20 | 월례회 업로드 PDF 원본은 보관하지 않음 | 서버·R2 확인 |

### 3.4 시크릿 관리
| ID | 요구 | 검증 |
|---|---|---|
| NFR-SEC-21 | 시크릿을 저장소에 커밋하지 않음 | `.gitignore` + **CI 시크릿 스캔** + `git log -p` 검색 |
| NFR-SEC-22 | `NEXT_PUBLIC_` 접두사는 공개 가능한 값에만 | 코드 리뷰 |

| NFR-SEC-24 | CI용 더미 시크릿은 `allowlist-secret` 명시 | 코드 리뷰 |

### 3.5 입력·요청
| ID | 요구 |
|---|---|
| NFR-SEC-25 | 모든 서버 입력은 Bean Validation 검증 |
| NFR-SEC-26 | 새가족 폼: 동일 IP 5분 5회 초과 거부 (rate limit) |

### 3.6 ⚠️ 달성 불가 항목 (명시)
| 항목 | 왜 불가능한가 | 대체 통제 |
|---|---|---|
| **월례회 스크린샷 차단** | 브라우저에 차단 API 없음. iOS는 네이티브도 불가. 타 기기 촬영은 원천 불가 | 열람 기간 제한 + **워터마크 burn-in** + 열람 로그 |
| **머지 강제 차단** | 무료 Private 저장소는 GitHub 브랜치 보호 사용 불가 | CI 상태 표시 + 팀 규칙 (`CICD.md` §4) |
| **push 차단** | CI는 push 이후에 실행됨. 로컬 훅은 `--no-verify`로 우회 가능해 폐기 | `feat/*`에는 깨진 커밋 허용, **머지 지점에서 통제** |

> **이 한계를 운영진에게 반드시 고지해야 합니다.** 막았다고 믿고 더 민감한 자료를 올리는 것이 가장 위험한 결과입니다.

## 14. 요구 간 상충과 해소

설계에서 실제로 부딪힌 지점들입니다.

| 상충 | 해소 |
|---|---|
| 사진 원본 화질 ↔ 비용 $0 | **비용 우선.** 2560px 리사이즈 보관. 원본은 사역팀 별도 보관 |
| 회원 편의(캐싱) ↔ 보안 | **보안 우선.** 서비스워커는 회원 데이터를 캐싱하지 않음 — 화이트리스트 방식이고 `/_next/image`(회원 사진 경로)까지 제외한다. 그래서 **오프라인에서는 공개 페이지 이미지도 안 보인다** |
| 월례회 캡처 차단 ↔ 기술적 한계 | **한계 인정.** 워터마크·기간제한·로그로 대체하고 한계를 고지 |
| 공개 영역 속도 ↔ 최신 공지 반영 | 정적 생성 + ISR. 백엔드 의존 없음을 우선 |
| 브랜치 보호 강제 ↔ 비용 $0 | CI 상태 표시 + 머지 규칙으로 대체 |
| 개발 속도 ↔ 인가 테스트 작성 부담 | **테스트 우선.** RLS가 없어 대체 수단이 없음 |
