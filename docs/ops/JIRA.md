## 0. 먼저 정할 것 — Jira가 무엇을 대체하는가

지금 이 프로젝트의 일감은 **GitHub 이슈·PR**과 **`docs/`의 문서 4종**(handover ·
DECISIONS · BACKEND_HANDOFF · WORKPLAN)에 흩어져 있다. Jira를 여는 목적이
"하나 더 늘리는 것"이 되면 **2인 팀에서 가장 비싼 실패**가 된다 —
`INTEGRATION.md §1`이 경고하는 관리 비용이 그대로 늘어난다.

그래서 경계를 먼저 못 박는다.

| 담는 곳 | 담는 것 | 담지 않는 것 |
|---|---|---|
| **Jira** | **"누가 · 무엇을 · 언제까지 · 지금 어디까지"** — 할 일 단위의 상태와 담당 | 설계 근거, 결정 이유, 계약 명세 |
| **GitHub PR** | 코드 변경과 리뷰·CI. 머지 게이트는 그대로 CI(`FLOW.md §4`) | 일정·우선순위 |
| **GitHub 이슈** | ⚠️ **Jira 개설 후에는 새로 만들지 않는다** (§8.3 이관) | — |
| `docs/spec/*` | 확정 스펙·API 계약 | 진행 상태 |
| `docs/records/DECISIONS.md` | PM 결정과 그 이유 (자동 기록) | 작업 티켓 |
| `docs/handover/` | 하루 끝의 "못 한 것 · 검증 못 한 것" | 티켓 대체 아님 |

> **한 줄 규칙: 상태는 Jira에, 이유는 `docs/`에, 코드는 PR에.**
> 세 곳에 같은 내용을 적기 시작하면 반드시 한 곳이 낡는다.

## 2. 이슈 타입 — 4개만 쓴다

| 타입 | 무엇을 담는가 | 크기 기준 | 예 |
|---|---|---|---|
| **Epic** | 마일스톤·상시 트랙 (§3) | 몇 주 | `M4 운영·문서·월례회·품질` |
| **Story** | **사용자가 화면에서 얻는 결과** | 4~16h · 최대 며칠 | `주보 업로드가 실제 R2에 저장된다` |
| **Task** | 사용자에게 안 보이지만 해야 하는 일 | 1~8h | `Vercel Production Branch 전환` |
| **Bug** | 이미 있는 것이 틀리게 동작 | — | `resetPasswordWithCode가 새 비밀번호를 저장하지 않는다` |

- **Sub-task는 기본적으로 쓰지 않는다.** 2인 팀에서 계층이 3단이 되면 보드에서
  상태를 두 번 옮기게 된다. 16h가 넘으면 Sub-task로 쪼개는 대신 **Story를 둘로 나눈다**
- ⚠️ **"조사·확인"만 하는 일도 Task로 만든다.** 지금 `handover/`에 쌓이는
  "눈으로 확인 못 한 것"이 정확히 이 부류이고, 티켓이 없으면 며칠씩 이월된다
  (Vercel 검증이 실제로 5일 걸렸다 — `handover/2026-09-01 §3.3`)

## 4. 필드와 라벨

### 4.1 쓰는 필드
| 필드 | 규약 |
|---|---|
| 담당자(Assignee) | **비우지 않는다.** 남이 답해야 하는 것은 상대에게 배정한다 |
| Epic Link | 필수 — 에픽 없는 티켓은 만들지 않는다 |
| **추정(Original Estimate)** | **시간(h) 단위.** 스토리 포인트를 쓰지 않는다 — `WORKPLAN`이 전부 시간 산정이라 환산하면 근거를 잃는다 |
| Sprint | §6 |
| Component | `frontend` · `backend` · `infra` · `docs` — 저장소 소유권(`INTEGRATION §2.2`)과 같은 이름 |

### 4.2 라벨 (6개만)
| 라벨 | 언제 | 왜 필요한가 |
|---|---|---|
| `contract` | API 계약이 바뀌거나 확인이 필요할 때 | PR 제목 `[CONTRACT]` 규칙과 짝 (`FLOW.md §4`) |

## 5. 워크플로 — 5단계

```
To Do ──▶ In Progress ──▶ In Review ──▶ Done
             │                 ▲
             └──▶ Blocked ─────┘
```

| 상태 | 들어가는 조건 | 나오는 조건 |
|---|---|---|
| **To Do** | 백로그에서 스프린트로 들어옴 | 착수 |
| **In Progress** | 브랜치를 팠다 (`FLOW.md [1]`) | PR 올림 |
| **In Review** | **PR이 열려 있고 CI가 돌고 있다** | 머지 + `develop` 동작 확인 |
| **Blocked** | 상대의 답·외부 서비스·PM 판단 대기 | 막힌 것이 풀림 |
| **Done** | §7 DoD 충족 | — |

- **`Blocked`를 라벨이 아니라 상태로 둔 이유**: 라벨로만 두면 보드에서 여전히
  "진행 중"으로 보인다. 실제로 "BE 답변 대기 4건"이 여러 날 진행 중처럼 보였다
- ⚠️ **`develop` 머지 = 배포**다(`FLOW.md [6]`). `In Review → Done`은
  **배포가 일어난다는 뜻**이므로, 환경변수 미등록 티켓을 이 문턱에서 걸러낸다

## 6. 스프린트

| 항목 | 값 |
|---|---|
| 길이 | **1주** (일 4h × 7일 = 28h/인) |
| 시작 | 월요일 |
| 용량 | 1인 **28h** → 계획은 **22h까지만** 담는다 (버그픽스·통합 여유) |
| BE 계수 | BE 티켓 추정은 **×1.2** (`WORKPLAN §1.1` 튜토리얼 수준 계수) |
| 회고 | 주 2회 동기화(`WORKPLAN §7`) 중 한 번을 스프린트 경계에 맞춘다 |

> **BE가 병목이다**(`WORKPLAN §1.2`). 스프린트를 담을 때 **BE 용량을 먼저 채우고,
> 남는 FE 용량에 검증·품질·문서 티켓을 넣는다.** 반대로 하면 FE 티켓만 닫히고
> 마일스톤은 안 움직인다.

## 7. 완료 정의(DoD)

**새로 만들지 않는다.** `WORKPLAN §7`의 DoD를 그대로 쓰고, Jira에서는 링크만 둔다.

| | 조건 |
|---|---|
| FE | 모바일·데스크톱 확인 · 로딩/빈/에러 상태 · mock 실패 케이스 통과 |
| BE | **인가 테스트 통과** · 규약대로 에러 응답 · Flyway 재현 가능 · Swagger 반영 |
| 공통 | `develop` 통합 후 동작 확인 |

추가 한 줄 — **`verify` 라벨이 붙은 티켓은 "실측 결과를 코멘트에 남긴 것"까지가 Done이다.**
스크린샷·curl 출력·수치 없이 닫지 않는다.

## 8. GitHub과의 연결

### 8.1 이름 규약
| | 형식 | 예 |
|---|---|---|
| 브랜치 | `feat/fe-LIGHT-12-짧은-설명` | `feat/be-LIGHT-31-attendance-api` |
| 커밋 | 기존 형식 **뒤에** 키를 붙인다 | `feat(be): 출석부 회차 API (LIGHT-31)` |
| PR 제목 | 기존 형식 + 키 | `feat(fe): 로그아웃을 /my 최상단으로 (LIGHT-18)` |

- 기존 커밋 규약(`feat(fe):` / `fix(be):`)은 **바꾸지 않는다.** 키만 덧붙인다
- ⚠️ **키를 브랜치에 넣는 것이 핵심**이다. GitHub for Jira 앱을 붙이면 브랜치·PR·커밋이
  티켓에 자동으로 달리고, 안 붙여도 사람이 눈으로 추적할 수 있다

### 8.2 연동 (선택 · 개설 후 별도 티켓)
- Jira Marketplace의 **GitHub for Jira**(무료)를 연결하면 개발 정보 패널에 PR 상태가 뜬다
- ⚠️ **스마트 커밋(`LIGHT-12 #done`)은 쓰지 않는다.** 커밋 메시지로 상태를 넘기면
  `In Review`(=배포 전) 단계를 건너뛰게 된다 (§5)

### 8.3 기존 GitHub 이슈 이관
- **열려 있는 것만** 옮긴다. 닫힌 이슈는 그대로 GitHub에 남긴다 (히스토리는 PR과 함께 있어야 읽힌다)
- 이관 시 본문을 다시 쓰지 않고 **원 이슈 링크 + 한 줄 요약**만 넣는다
- 대표 대상: **이슈 #133**(BE 전달 4건) → `blocked-be` 티켓 3~4개로 쪼갠다.
  하나로 묶여 있어서 "1번만 됐고 나머지는 어디까지인지"가 안 보인다

| E5 월례회 자료 | 27 | E10 품질·보안·오픈 | 32 |

**`Status` 열이 핵심이다 — `완료` 130건 · `대기` 157건.** 완료 130건은 이미 만든
것(대부분 FE mock 기준)이고, 2026-09-08에 **전부 Jira에 만들고 `완료`로 전이했다**
(PM 결정). 실제로 해야 할 일은 `대기` 157건이다.

**`Phase` 열 = 단계별 진행 순서**

| Phase | 뜻 | 건수 |
|---|---|---|
| `S0` | 이미 끝난 것 (기록용) | 104 |
| `S1` | M1 실연동 — 공개 공지·새가족·설교 API | 15 |
| `S2` | M2 인증 실연동 — 카카오·리셋 코드·통합 #2 | 30 |
| `S3` | M3 업로드 파이프라인·주보·사진첩 | 34 |
| `S4` | M4 월례회·문서·출석부·관리 | 63 |
| `S5` | 품질·보안·성능·접근성·정식 오픈 | 41 |

> Phase와 Status는 다른 축이다 — `완료` 130건 중 104건이 `S0`이고, 나머지 26건은
> `S2`·`S3`에 걸쳐 있다(이미 만들어 둔 mock 화면들). 그래서 `S0` 건수(104)와
> 완료 건수(130)가 일치하지 않는다.

> ⚠️ **테스트 티켓 61건은 구현과 분리해 만들었다.** 붙여 두면 "구현 끝났으니 Done"이
> 되고 테스트가 조용히 빠진다. 특히 **인가 테스트는 이 구조의 마지막 방어선**이라
> (DB에 RLS가 없다) 엔드포인트 그룹마다 별도 티켓으로 세웠다.

> ⚠️ 추정은 `WORKPLAN §6`의 시간을 **1pt≈2h · 2≈4h · 3≈6~8h · 5≈12h · 8≈20h**로
> 환산한 값이다. 입력 전에 `WORKPLAN`·`BACKEND_TASKS §10`과 한 번 대조한다.

## 11. 하지 않을 것

- **`docs/`를 Jira로 옮기지 않는다.** 결정·계약·인계는 저장소에 남는다 — 저장소는
  코드와 함께 버전이 붙고, Jira는 그렇지 않다
- **일일 인계를 티켓으로 만들지 않는다.** `handover/`는 그대로 쓰고, **거기서
  "남은 일"만 티켓으로 승격**한다
- **번다운 숫자를 맞추려 추정을 고치지 않는다.** `WORKPLAN §1.6`이 이미 ±25%를 전제한다
