## 1. 프로젝트 개요

### 1.1 배경
현재 청년교회는 모교회(김해교회, www.gloria.or.kr) 사이트의 `다음세대 > 청년교회` 하위 페이지 한 장으로만 존재한다.
- 모교회 사이트는 Wix 기반, 전 세대를 아우르는 전통적 구조 → 청년 타깃의 톤앤매너·정보 밀도와 맞지 않음
- 청년부 자체 소식/모임/신청 등이 담길 공간이 없음
- 새신자·전입 청년이 검색으로 도달할 독립 채널이 없음

### 1.2 목표
이 프로젝트는 성격이 다른 **두 개의 사이트를 한 몸에** 담는다.

| 영역 | 대상 | 목표 |

| **공개 영역** | 비로그인 방문자 | 처음 오는 청년이 "언제·어디로·누구를 찾아가면 되는지" 3초 안에 파악. 검색 유입 |

## 3. 정보 구조 (IA)

### 3.0 권한 모델
| 역할 | 코드 | 부여 방식 | 권한 |
|---|---|---|---|
| 방문자 | `GUEST` | 비로그인 | 공개 영역만 |
| 일반 회원 | `MEMBER` | 가입 후 **관리자 승인** | + 주보 열람, 사진첩 열람·다운로드, 내부 공지 |
| 임원 | `LEADER` | 전도사님이 지정 | + 공지·주보·사진 작성·업로드·삭제, **회의록·예산안 열람·작성** |
| 목회자 | `PASTOR` | 최초 수동 지정 | + 회원 승인, 권한 부여, 회원 정보 열람 |

- **가입 즉시 회원이 되지 않는다.** 가입 → `PENDING` → 관리자 승인 → `MEMBER`.
  승인 절차가 없으면 아무나 가입해서 내부 자료를 볼 수 있다. 이 프로젝트에서 타협 불가 항목.
- 권한은 **서버에서 검사한다.** 메뉴를 숨기는 건 UI 편의일 뿐 보안이 아니다.
- `PASTOR` 전용 권한은 **회원 관리 하나뿐**이다(2026-08 결정: 임원도 예산안 접근). 역할 단계가 단순해져 실수 여지가 줄었다.

### 3.1 구조

```
[공개 영역] — 로그인 불필요, 검색엔진 허용
HOME
├─ 소개 (LIGHT / 섬기는 사람들 / 한 해의 흐름)
├─ 예배와 모임 (주일 14:00 · 마을모임 섹션)
├─ 말씀 (설교 영상 - YouTube)
├─ 오시는 길
└─ 처음 오시는 분 ★ 헤더 CTA 상시 노출
    └─ 새가족 등록 (폼)

[회원 영역] — 로그인 + 승인 필요, 검색엔진 차단(noindex)
└─ 나의 LIGHT
    ├─ 주보           (주차별 열람 · 다운로드)
    ├─ 사진첩         (행사 앨범 · 개별/일괄 다운로드)
    ├─ 공지 (내부)     (회원 대상 공지)
    ├─ 월례회 자료      ★ 열람 기간 내에만 · 보기 전용
    └─ 내 정보         (프로필 · 비밀번호 · 탈퇴)

[운영 영역] — LEADER 이상, 검색엔진 차단
└─ 관리
    ├─ 콘텐츠 작성 (공지 · 주보 업로드 · 앨범 생성/사진 업로드)
    ├─ 회의록                        [LEADER+]
    ├─ 예산안                        [LEADER+]
    ├─ 월례회 자료 업로드·기간 설정    [LEADER+]
    ├─ 회원 관리 (승인 · 권한 부여)    [PASTOR only]
    └─ 새가족 등록 내역               [LEADER+]
```

### 3.2 IA 원칙
- 공개 영역 상단 메뉴 **5개 이하** + 우측에 `처음이신가요` CTA
- 로그인 상태에서는 헤더 우측이 CTA → **프로필 아바타**로 전환, 여기서 회원/운영 영역 진입
- 회원 영역을 공개 메뉴에 섞지 않는다. 비로그인 방문자에게 잠긴 문을 보여주면 혼란만 준다
- 관리 메뉴는 권한이 있는 사용자에게만 렌더 (동시에 서버에서도 차단)
- 모교회 사이트 링크는 푸터에 1개

### 4.2 처음 오시는 분
**이 페이지가 사이트 전체에서 가장 중요하다.** 드림센터가 본당과 별개 건물이라, 주소만 보고 온 청년은 본당에 도착해서 길을 잃는다. 이게 최대 이탈 지점.

- **건물 찾기 안내를 최상단에**:
  - 본당(가락로 117)과 드림센터의 위치 관계를 보여주는 **약도 또는 사진** (지도 핀 하나로는 부족)
  - 드림센터 **외관 사진** + 입구 사진 → "이 건물입니다" 시각 확인
  - 본당 앞에 도착한 경우의 도보 경로 ❓(거리·소요시간)
- **주일 타임라인** (실제 시각 기준):

  | 시각 | 무엇 |
  |---|---|
  | ~11:20 | 드림센터 4층 도착, 입구에서 안내받기 |
  | 11:30 | 청년예배 |
  | 예배 후 | ❓ 점심·교제 (11:30 예배와 15:30 마을모임 사이 공백 안내 필요) |
  | 15:30~16:00 | 마을모임 (처음이면 **새가족마을**) |

  → 14:00 예배 ~ 15:30 마을모임이 자연스럽게 이어져 타임라인 공백 없음. 처음 오는 청년에게 "예배만 보고 가도 되고, 마을까지 있어도 된다"를 명시할 것
- 주차 안내 — **드림센터 기준** 주차장 위치 (본당 주차장과 다른지 확인 ❓), 실제 사진 포함
- 대중교통 안내
- FAQ 5~7개: 뭐 입고 가나 / 헌금 해야 하나 / 몇 살까지 청년부인가(20~39세 또는 결혼 전) / 혼자 가도 되나 / 마을은 꼭 들어가야 하나
- 하단: 새가족 등록 폼 + 카카오톡 문의 링크 ❓

### 4.4 마을모임 — 개별 페이지 없음 (결정)
**마을별 상세 페이지는 만들지 않는다.** 마을 명칭이 번호 체계(1~9마을)라 페이지를 만들어도 방문자에게 전달되는 정보가 적고, 마을장·구성이 학기마다 바뀌어 관리 부담만 남는다.

대신 `예배와 모임` 페이지 안의 **한 섹션**으로 처리:
- 마을 구성: 1마을 ~ 9마을 + **새가족마을**
- 시간: 주일 예배 종료 후 **15:30 ~ 16:00 (약 30분)**, 드림센터
- 새가족마을 한 단락 + `처음 오시는 분` 페이지로 링크
- 텍스트 위주 → Notion 관리 불필요, 코드 내 상수로 유지 (연 1~2회 수정)

> 나중에 마을별 사진·소개를 모아 카드로 보여주고 싶어지면 Phase 3에서 재검토.

### 4.5 공지사항 (공개 / 내부 2종)
공지는 **공개 여부를 글마다 선택**한다. 하나의 게시판에 플래그로 구분.
- 공개 공지: 수련회 안내처럼 외부에 알려도 되는 것 → HOME "이번 주"에 노출, 검색 허용
- 내부 공지: 회원 대상 전달사항 → 로그인 회원만
- 작성: `LEADER` 이상. 제목·본문(리치텍스트)·첨부파일·상단고정·공개범위
- 목록: 상단고정 우선, 최신순. 비로그인 방문자에게는 공개 공지만 보임

### 4.6 주보 (회원 전용) — 이미지 확정
매주 제작되는 주보를 아카이브. **형식은 이미지 파일**(확정).
- 업로드: `LEADER` 이상. 주일 날짜 + 이미지 N장(순서 지정)
- 열람: `MEMBER` 이상. **최신 주보가 자동으로 열리고**, 이전 주차는 아래 목록에서 선택
- 뷰어: 스와이프 슬라이드 + 핀치 줌 → **사진첩 라이트박스를 재사용**하므로 추가 구현 비용이 거의 없다
- ⚠️ 주보는 글자가 작다 → 썸네일이 아니라 큰 이미지를 바로 로드해야 읽힌다 (사진첩과 다른 점)
- 다운로드 허용

### 4.7 사진첩 (회원 전용) ★ 재방문의 핵심
행사가 끝나면 사진 수백 장이 공유되는데, 이걸 담는 곳.

**구조**: 앨범(행사 단위) → 사진 그리드 → 확대 보기
- **업로드** (`LEADER` 이상): 앨범 생성 후 **다중 선택 업로드**. 200장 이상을 한 번에 올릴 수 있어야 하며, 진행률 표시와 부분 실패 재시도가 필요하다
- **열람** (`MEMBER` 이상): 썸네일 그리드 → 탭하면 원본 확대, 좌우 스와이프
- **다운로드**:
  - 개별: 확대 화면에서 원본 다운로드 버튼
  - 선택 다운로드: 체크박스로 여러 장 골라 ZIP 묶음 다운로드
  - 앨범 전체 다운로드는 용량이 커서 기본 비활성 (필요 시 `LEADER`만)
- 정렬: 촬영일시 또는 업로드순
- ⚠️ **초상권**: 얼굴이 담긴 사진이 다운로드된다. 로그인 회원 한정이 최소 방어선이며,
  "사진 내려달라" 요청 창구(신고/삭제 요청)를 만들어야 한다 ❓

### 4.8 회의록 · 예산안 (LEADER 이상)
내부 문서. **문서 게시판 하나**로 구현하고 분류로만 나눈다.
- 공통 구조: 제목 · 작성일 · 본문 · 첨부파일 · 작성자
- **회의록과 예산안의 접근 권한이 동일**(임원 이상)해졌으므로, 실질적으로 같은 게시판의 두 분류다
- 첨부파일은 **서명된 임시 URL**로만 내려간다. 파일 주소를 아는 것만으로 열려서는 안 됨
- 목록/상세/첨부 모두 `noindex` + 서버측 권한 검사
- ❓ 확인: 예산안 **작성**도 임원이 가능해야 합니까? (현재 설계는 열람·작성 모두 임원 허용)

> 권한이 같아진 덕에 RLS 정책이 하나로 합쳐졌다. 정책이 단순해지는 것은 보안상 이득이다 — 실수할 지점이 줄어든다.

### 4.8b 월례회 자료 (회원 열람 · 기간 제한) ★신규
2개월마다 열리는 월례회 자료를 **보기 전용**으로 제공하고, 월례회가 끝나면 열람을 차단한다.

**요구와 현실**
- 요구: 캡처·다운로드 불가 + 월례회 종료 후 열람 불가
- ⚠️ **웹에서 스크린샷 차단은 원천적으로 불가능하다.** 브라우저에 그런 API가 없고, iOS는 네이티브 앱에서도 막을 수 없다. 다른 기기로 화면을 찍는 것도 막을 수 없다
- → 목표를 **"쉬운 유출 차단 + 유출 시 추적"** 으로 재정의한다 (`ARCHITECTURE.md §7.7`)

**구현하는 통제**
| 통제 | 강도 |
|---|---|
| **열람 기간 제한** (서버 강제) | 강함 — 요구사항의 핵심 |
| **다운로드 경로 차단** (파일 URL 미발급, 서버 스트리밍) | 강함 |
| **워터마크 burn-in** (이름·연락처 뒷4자리·시각) | **가장 실효적** |
| 우클릭·롱프레스 저장 차단 | 약함 (개발자도구로 우회 가능) |
| 열람 로그 (누가·언제·몇 페이지) | 중간 |

**핵심은 워터마크다.** 캡처를 막을 수 없으므로 "캡처하면 내 이름이 박힌다"는 사실이 실제 억제력을 만든다.

- 열람: `MEMBER` 이상, **열람 기간 내에만**. 기간 종료 후 목록에는 `종료됨`으로 남고 열 수 없다
- 업로드·기간 설정: `LEADER` 이상. 기간 연장·조기 종료 가능
- ✅ **임원(LEADER) 이상은 기간 제약 없이 열람 가능** (자료 준비·사후 확인)

**원본이 Word 문서다 — 변환 경로**
자료는 Word로 작성되는데, 다운로드 차단과 워터마크를 걸려면 **페이지 이미지**가 필요하다. Word를 그대로 보여주면 원본이 클라이언트로 내려가 다운로드를 막을 수 없다.

→ **업로더가 Word에서 「PDF로 저장」한 뒤 PDF를 올리고, 서버가 페이지 이미지로 변환한다.**
서버에 LibreOffice를 설치해 자동 변환하는 방식도 있으나 채택하지 않았다:
- Docker 이미지 +700MB, 변환 시 메모리 스파이크 → **무료 호스팅 512MB에서 위험**
- **컨테이너에 한글 폰트가 없으면 문서가 `□□□`로 렌더된다** (이 방식의 가장 흔한 실패)
- PDF 경유는 폰트가 PDF에 임베드되어 오므로 이 문제가 아예 없고, 레이아웃도 Word 원본과 100% 일치

업로더 부담은 **클릭 1회**(다른 이름으로 저장 → PDF)다. 상세는 `ARCHITECTURE.md §7.7`.
- **업로드한 PDF 원본은 서버에 보관하지 않는다.** 남겨두면 그 자체가 유출 경로가 된다
- ⚠️ **운영진에게 "캡처를 완전히 막을 수 없다"는 점을 반드시 전달해야 한다.** 막았다고 믿고 더 민감한 자료를 올리는 것이 가장 위험한 결과다

### 4.9 인증 화면
- 회원가입: 이름 · 이메일(또는 카카오 로그인) · 비밀번호 · 마을(1~9/새가족) · 연락처 · 개인정보 동의
- 가입 직후: "관리자 승인 후 이용 가능합니다" 대기 화면 (`PENDING`)
- 로그인 / 비밀번호 재설정
- **카카오 로그인 도입 확정** (이메일 로그인과 병행)
- ⚠️ 카카오에서 **이메일을 받으려면 "비즈 앱" 전환이 필요**하고, 그러려면 사업자등록번호 또는 고유번호증이 있어야 한다
  → ❓ **교회 고유번호증으로 전환 가능한지 확인 필요**
  → 전환이 안 되더라도, 카카오 로그인 후 앱 안에서 이름·연락처·마을을 직접 받으면 진행 가능하다
- 카카오 닉네임은 실명이 아닌 경우가 많아, **이름·연락처·마을은 어느 경우든 앱에서 직접 받는다** (승인 대조용)

### 4.10 회원 관리 (PASTOR 전용)
- 승인 대기 목록 → 승인 / 거절
- 회원 목록: 이름·마을·역할·가입일, 역할 변경(MEMBER ↔ LEADER)
- 탈퇴 처리
- ⚠️ 마지막 `PASTOR`의 권한을 스스로 내리지 못하게 막을 것 (자기 잠금 방지)

### 6.1 (구) Supabase 단일 구성 — 폐기
v1.x에서는 Supabase(인증·DB·스토리지·RLS)를 단일 백엔드로 쓰려 했으나, **BE 담당자의 Spring Boot 학습이 프로젝트 목표에 포함**되면서 Spring Boot REST API로 전환했다.

⚠️ **이 전환으로 RLS(DB 행 단위 권한)를 잃었다.** v1.x에서는 코드에서 권한 검사를 빠뜨려도 DB가 막아줬지만, Spring이 단일 계정으로 접속하는 구조에서는 그 방어선이 없다.
→ **인가 테스트 매트릭스**(`ARCHITECTURE.md §5.3`)가 이를 대체한다. 선택이 아니라 필수다.

### 6.2 파일 저장 — 비용 $0 확정
**결정: 월 비용이 발생하면 진행하지 않는다.** → Cloudflare R2 **무료 10GB** 안에서만 운영한다.
R2를 고른 결정적 이유는 **전송량(egress)이 무료**라는 점이다. 사진 다운로드가 핵심 기능이라, 전송량 과금이 있는 서비스는 회원이 많이 쓸수록 비용이 오른다.

**10GB 안에서 버티는 방법 — 원본을 보관하지 않는다**

| 전략 | 장당 | 10GB 수용량 |
|---|---|---|
| 원본(5MB) 보관 | 5.15MB | 약 1,900장 (2년) |
| **장변 2560px 리사이즈** ★ | 1.35MB | **약 7,400장 (7년)** |

- 업로드 시 **브라우저에서 장변 2560px로 리사이즈**한 뒤 전송. 업로드 시간도 함께 줄어든다
- 열람용 썸네일(640px)을 따로 저장해, 앨범 200장을 열어도 전송량이 16MB 수준
- 2560px는 휴대폰 감상·SNS 공유·A4 인쇄에 충분하다
- ⚠️ **인쇄·보정용 원본은 이 사이트의 역할이 아니다.** 사역팀이 별도 보관(구글 드라이브·외장하드)하고, 사이트는 감상·공유·저장을 담당한다. 이 경계를 회원에게도 안내할 것

**용량 초과 방지 장치 (필수)**
- 관리 화면에 사용량 표시(`4.2GB / 10GB`), 80% 경고, **95%에서 업로드 차단**
- 앨범 삭제 시 R2 객체도 삭제 (안 하면 용량이 조용히 샌다)
- 오래된 앨범 아카이브 기능은 Phase 3

**⚠️ Supabase 무료 플랜**: 약 7일간 활동이 없으면 프로젝트가 일시정지된다. 주일마다 접속이 있으면 문제없지만, 방학·개발 중단 구간에서 멈출 수 있다 → 운영 매뉴얼에 "사이트가 안 열릴 때" 항목으로 남긴다.

### 6.3 "앱으로도" — PWA로 접근
| 방식 | 설치 | 푸시 | 비용/기간 | 판단 |
|---|---|---|---|---|
| **PWA** | 홈 화면 추가 | Android ○ / iOS △(설치 시 가능) | 추가 작업 소규모 | ★ Phase 2 |
| Capacitor 래핑 | 스토어 배포 | ○ | 개발자 계정 연 $99+$25, 심사 | Phase 4 재검토 |
| React Native 재작성 | ○ | ○ | 코드베이스 2개 | 과함 |

**PWA로 충분한 이유**: 이 앱의 기능은 문서 열람·사진 다운로드다. 카메라·블루투스 같은 네이티브 API가 필요 없다. `manifest.json` + 서비스워커 + 아이콘만 추가하면 홈 화면에서 앱처럼 실행되고, 상단 브라우저 UI도 사라진다.
- 사진 다운로드는 iOS Safari PWA에서 동작 확인이 필요하다 ❓ (검증 항목)
- 스토어 배포가 꼭 필요해지면 그때 Capacitor로 같은 코드를 감싼다 → **처음부터 웹으로 만드는 것이 앱 전환의 최단 경로**

### 6.4 운영 원칙
- 콘텐츠 업데이트에 코드 수정이 필요한 구조를 만들지 않는다 → 관리 화면에서 전부 처리
- 권한 검사는 **UI 숨김 + 서버 검증 + DB RLS** 3중으로 한다
- 파일은 공개 URL을 갖지 않는다. 전부 서명된 임시 URL

### 6.5 인수인계 산출물
- 관리자 매뉴얼 (공지 쓰기 / 주보 올리기 / 사진 올리기 / 회원 승인)
- 계정 소유권 문서 (Supabase / R2 / Vercel / 도메인 / 카카오 개발자) — **전부 교회 명의**
