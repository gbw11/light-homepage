## 2. 협업 모델 — 물리적으로 분리된 두 프로젝트

Spring Boot 백엔드가 되면서 FE와 BE는 **다른 언어, 다른 프로세스, 다른 배포**가 됐다. 경계가 저절로 생긴다.

```
모노레포 1개
light-homepage/
├─ frontend/   Next.js       ← FE 단독 소유
├─ backend/    Spring Boot   ← BE 단독 소유
└─ docs/       계획 문서       ← 공동
```
- **파일 충돌이 구조적으로 발생하지 않는다.** 디렉터리 소유권 논쟁이 필요 없다
- 저장소를 2개로 쪼개지 않는 이유: 2인 팀에서 이슈·PR·문서가 흩어지면 관리 비용만 늘어난다
- 대신 **접점이 API 하나로 집중**된다 → §4의 계약이 그만큼 중요해졌다

| | |
|---|---|
| 장점 | 서로의 코드를 볼 필요 없음. 각자 익숙한 도구·테스트·디버깅 |
| 장점 | BE는 Spring에만 집중 → 학습 목표에 부합 |
| **위험** | **API가 안 맞으면 통합이 전부 막힌다.** v1.x의 타입 자동 공유를 잃었다 |
| 대응 | §4 계약 선확정 + FE mock 계층 + Swagger UI |

## 4. 경계 계약 (Contract) — W0에 확정

FE와 BE가 다른 언어라 **타입이 자동으로 공유되지 않는다.** 계약을 문서로 못 박아야 한다.

### 4.1 계약의 3요소
| # | 산출물 | 담당 | 시점 |
|---|---|---|---|
| 1 | 엔드포인트 목록(경로·메서드·권한) | 공동 확정 | W0 — `ARCHITECTURE.md §6.2`가 초안 |
| 2 | 요청/응답 JSON 형태 | BE 초안 → 공동 합의 | W0 |
| 3 | 공통 응답·에러 규약 | 공동 | W0 |

### 4.2 공통 규약
```json
{ "data": { } }
{ "error": { "code": "FORBIDDEN", "message": "권한이 없습니다.", "field": null } }
{ "data": { "items": [], "page": 0, "hasNext": true } }
```
- 에러 `code`는 **FE가 분기에 쓰는 값**이므로 문자열 집합을 미리 고정한다:
  `UNAUTHORIZED · FORBIDDEN · NOT_FOUND · VALIDATION_ERROR · PENDING_APPROVAL · STORAGE_LIMIT · DUPLICATE`
- 날짜는 전부 ISO-8601. `LocalDate`는 `"2026-08-24"`, 시각은 UTC + `Z`
- **ID는 문자열로 직렬화**한다 (JS `Number` 정밀도 이슈 회피)
- 파일 URL은 항상 presigned URL. FE는 R2 경로를 알지 못한다

### 4.3 FE의 mock 계층 — BE를 기다리지 않는 장치
```
frontend/src/lib/api/
├─ index.ts    # FE는 항상 이것만 import
├─ mock.ts     # 계약에 맞는 가짜 응답 + 지연 300ms
└─ real.ts     # 실제 fetch
# .env: NEXT_PUBLIC_USE_MOCK=1
```
- **FE는 `real.ts`를 직접 import하지 않는다.** 이 규칙 하나로 병렬 작업이 가능해진다
- mock에 **실패 케이스를 반드시 넣는다**: 401·403·`STORAGE_LIMIT`·업로드 실패·빈 목록.
  성공 경로만 만들면 통합 때 무너진다

### 4.4 Swagger UI = 살아있는 계약서
BE가 `springdoc-openapi`를 M1 초반에 붙인다. 이후 FE는 `localhost:8080/swagger-ui.html`에서 실제 형태를 확인한다.
- ⚠️ Swagger는 구현된 뒤에 생기므로 **W0의 사전 합의를 대체하지 못한다**
- 계약 변경 시 즉시 상대에게 알린다. 조용히 바꾸면 상대 작업이 통째로 어긋난다

## 5. 역할 정의

| | **BE (Spring Boot)** | **FE (Next.js)** |
|---|---|---|
| 핵심 책임 | 데이터·권한·파일이 **안전하고 정확하게** | 사용자가 **막히지 않고** 목적 달성 |
| | Flyway 스키마·마이그레이션 | 디자인 시스템·컴포넌트 |
| | Spring Security·JWT·카카오 OAuth | 페이지·라우팅·레이아웃 |
| | `@PreAuthorize` + Service 재검사 | 권한별 UI 분기(메뉴 숨김) |
| | **인가 테스트 매트릭스** ★최우선 | 폼·클라이언트 검증·에러 표시 |
| | R2 presigned URL·용량 집계·차단 | **브라우저 이미지 리사이즈** |
| | ZIP 스트리밍·다운로드 라우트 | **사진 업로더 UI**(진행률·재시도) |
| | REST API·OpenAPI 문서 | 라이트박스·주보 뷰어·리치텍스트 |
| | 메일 발송·시드 스크립트·배치 | Vercel 배포·SEO·PWA·반응형·접근성 |
| | Docker·Render 배포·DB 운영 | |
| 품질 게이트 | `ARCHITECTURE.md §13` 보안 체크리스트 | 모바일 실기기 확인 · Lighthouse 90+ |

### 5.1 권한 구현의 책임 분리
| 층 | 담당 |
|---|---|
| UI 숨김 | FE — **보안이 아니다.** 편의 기능임을 FE도 인지할 것 |
| Controller `@PreAuthorize` | BE |
| Service 재검사 | BE |
| **인가 테스트 매트릭스** | BE — RLS를 잃은 v2.0의 마지막 방어선 |

⚠️ FE는 "메뉴를 숨겼으니 됐다", BE는 "UI에서 안 보이니 됐다"고 판단하지 않는다.
**둘 다 상대가 막아줄 것으로 가정하면 아무도 막지 않는다.**

### 8.2 ⚠️ 최대 위험: 사진 업로드
파일이 Spring을 통과하지 않고 브라우저 → R2로 직접 간다(`ARCHITECTURE.md §7.3`).

```
FE 책임                          │ BE 책임
─────────────────────────────────┼────────────────────────────────
파일 선택(다중)                  │ uploads:issue — photoId 발급 +
브라우저 리사이즈 2560/640       │   presigned PUT URL 2개 반환
동시 3~4개 큐 제어               │ 용량 한도 검사 → 95% 시 거부
R2로 PUT 직접 전송               │ uploads:commit — COMMITTED + 용량 기록
진행률 · 부분 실패 재시도        │ 미커밋(PENDING) 정리 배치
이탈 경고                        │
```
**W0에 합의할 것**
| 항목 | 결정안 |
|---|---|
| presigned URL 유효시간 | 15분, 배치로 나눠 재발급 |
| 재시도 | 같은 photoId로 URL 재발급 (고아 방지) |
| commit 단위 | 20장 배치 |
| 리사이즈 실패(HEIC 등) | 건너뛰고 사용자에게 목록 표시 |

> **권장: M1 기간 중 각자 2시간을 떼어 "사진 1장 업로드" 프로토타입을 관통시킨다.**
> M3에 처음 붙이면 실패했을 때 되돌릴 시간이 없다. 가장 위험한 접점을 가장 먼저 검증한다.
> 이 2시간은 §11 산정에 **포함되어 있지 않다** — 추가 투자로 보되, 수십 시간을 아낀다.

### 8.3 배포 프록시 (M1 말에 확인)
`ARCHITECTURE.md §6.3` — Next.js `rewrites`로 `/api/**`를 Spring에 프록시해 동일 출처로 만든다.
- FE: `next.config.ts` rewrites + `API_ORIGIN`
- BE: 쿠키 `HttpOnly; Secure; SameSite=Lax`, `Origin` 검증
- **M1 배포 때 이 경로를 미리 관통시킨다.** M2에서 인증과 프록시를 동시에 디버깅하면 시간이 두 배로 든다
