# 과금 방지 설계

**목표: 어떠한 경우에도 과금이 발생하지 않는다.**

`WORKPLAN.md §1`의 제약("월 비용 $0")과 `ARCHITECTURE.md §9`의 전제를 **지키는
방법**을 담는다. 무엇을 쓸지 고른 근거는 `ARCHITECTURE.md §4`·`§8`에 있고,
여기는 **그 선택이 어떻게 강제되는지**만 다룬다.

담당: PM/인프라 (`server_develop`)

---

## 0. 원칙 — 한도를 지키는 것으로는 부족하다

"사용량을 무료 한도 아래로 유지한다"는 **지키면 $0**이다. 트래픽 급증 한 번,
설정 실수 한 번, 잊어버린 대시보드 토글 하나로 깨진다. 그리고 **과금은 조용히
일어난다** — 화면도 API도 테스트도 전부 정상으로 보이고, 청구서로만 드러난다.

그래서 사용량을 관리하는 대신 **과금 경로 자체를 없앤다.**

| 층 | 장치 | 초과했을 때 일어나는 일 |
|---|---|---|
| **1차 (하드)** | 계정에 **결제 수단이 없다** · 지출 한도 $0 | 서비스가 **멈춘다** |
| **2차 (소프트)** | 코드·설정이 사용량을 한도 아래로 억제한다 | 멈추지도 않는다 |

> **중단은 사고, 과금은 재난.** 1차만 있으면 예고 없이 서비스가 멈추고, 2차만
> 있으면 실수 한 번에 청구된다. **2차가 1차보다 먼저 걸리도록** 설계한다.

### 0.1 그래서 하지 않는 것

- **무료 한도가 있어도 결제 수단을 요구하는 서비스는 채택하지 않는다.**
  그 서비스는 1차 방어가 불가능하다 (§3.6이 유일한 미결 사례)
- **"카드 등록하면 한도가 늘어난다"는 제안을 받지 않는다** — 늘어난 한도는
  넘을 수 있는 한도다
- 무료 한도를 근거로 **서비스를 두 개 띄우지 않는다** (§3.3)

## 1. 이 문서가 유일한 목록이다

**새 외부 서비스를 붙이는 PR은 §2 표에 행을 추가해야 한다.** 행이 없는 서비스는
도입하지 않는다. 도입 시점에 "무료니까 괜찮다"로 넘어간 서비스가 나중에 청구서에
나타나는 것을 막는 장치다.

## 3. 서비스별 상세

### 3.1 GitHub Actions — 무료 분이 소모된다

⚠️ **Public 저장소와 다르다.** 우리는 Private이므로 실행 시간이 **무료 분에서
차감된다** (Free 플랜 2,000분/월).

**현재 사용량** (2026-08, 실측):

| 워크플로 | 실행 수 | 실행 시간 합계 |
|---|---|---|
| Frontend CI | 185회 | 약 201분 |
| Backend CI | 37회 | 약 35분 |
| **합계** | **222회** | **약 236분** (잡별 분 단위 올림 감안 ~300분) |

한도의 약 15%다. 여유는 있지만 **실행 수가 이미 222회**라는 점이 문제였다 —
`feat/*` push와 PR이 같은 커밋을 두 번 검증한다.

**2차 가드**
- `paths` 필터 — `frontend/**` 변경은 Backend CI를 돌리지 않고, 그 반대도 같다
  (이미 적용, `docs/CICD.md §1.1`)
- **`concurrency` 취소** — 같은 브랜치·PR에 새 커밋이 오면 앞의 실행을 취소한다.
  ⚠️ `develop`은 취소하지 않는다: `deploy` 잡이 Render 훅을 호출하는 중에 끊기면
  배포가 트리거됐는지 알 수 없는 상태가 된다

**1차 차단** — GitHub Actions의 기본 지출 한도는 $0이고, 그 상태에서 무료 분을
넘기면 **과금이 아니라 워크플로 실행 거부**로 나타난다. §4 체크리스트로 확인한다.

### 3.2 Neon — ★ 여기가 실제로 새고 있었다

**증상 없이 한도를 넘는 구조였다.**

`/actuator/health`에는 Spring Boot가 DataSource 인디케이터를 자동으로 붙인다.
그리고 `infra/render/README.md`는 cron-job.org로 **10분마다 그 경로를 때리도록**
설계돼 있었다. 결과:

```
10분 핑 → /actuator/health → DB 커넥션 검증 쿼리 → Neon 자동 정지 안 걸림
        → 월 744시간 상시 가동
```

`ARCHITECTURE.md §8.2`는 **"유휴 시 자동 정지되나 재개가 빠르다"**를 근거로 무료
판정을 했다. **그 전제가 핑 설계와 정면으로 충돌한다** — 자동 정지가 한 번도
걸리지 않는다.

### `/actuator/health`를 때리는 경로는 **셋**이었다

하나만 고쳐도 나머지가 Neon을 깨워둔다. 셋 다 막아야 의미가 있다.

| # | 누가 | 주기 | 막은 방법 | 확인 |
|---|---|---|---|---|
| 1 | **cron-job.org 슬립 방지 핑** | 10분 | 핑 URL을 `/actuator/health/alive`로 | ✅ 2026-08-27 |
| 2 | **HikariCP 커넥션 풀 keepalive** | **2분** | `keepalive-time: 0` (§아래) | ✅ CI 테스트로 고정 |
| 3 | **Render 자체 헬스체크** | 상시 | Health Check Path를 `/actuator/health/alive`로 | ✅ 2026-08-27 |

⚠️ **2번은 코드를 읽어야만 보인다** — HikariCP 6.3.3의 기본값이 0이 아니라 2분이다.
⚠️ **3번은 배포 성공으로 판별되지 않는다** — 예전 값도 200을 주므로 배포는 통과한다.

**셋 다 증상이 없다.** 화면·API·테스트가 전부 정상으로 보이고, Neon 사용량으로만
드러난다.


**고친 방법** — 핑 전용 헬스 그룹을 만들어 DB를 빼놨다.

```yaml
# backend/src/main/resources/application.yml
management:
  endpoint:
    health:
      group:
        alive:
          include: ping     # ping 인디케이터만. DB·메일·외부 호출 없음
```

| 경로 | 용도 | DB 접근 |
|---|---|---|
| `/actuator/health/alive` | **슬립 방지 핑 · Render 헬스체크** | ❌ 없음 |
| `/actuator/health` | 사람이 진단할 때 | ✅ 있음 |

**왜 기본 `liveness` 그룹을 쓰지 않았나** — 기본 그룹 구성(`liveness` =
`livenessState`)은 프레임워크 기본값이라 Spring Boot 버전이 올라가며 조용히
바뀔 수 있다. `include`를 명시하면 우리 파일이 답을 갖는다.

**사람이 기억하지 않아도 되게 고정했다** —
`backend/src/test/java/kr/light/config/HealthProbeTest.java`가 `alive` 그룹에
`ping` 외의 것이 들어오면 CI에서 실패한다. 이 사고는 기능 테스트로는 절대
드러나지 않으므로(모든 화면이 정상으로 보인다) 테스트가 유일한 감지 수단이다.

> ⚠️ **트레이드오프**: 헬스체크가 DB를 보지 않으므로, **DB가 죽어도 Render는
> 서비스를 정상으로 판단한다.** 이건 의도한 것이다 — DB 장애로 컨테이너가
> 재시작 루프에 빠지는 것이 더 나쁘고, 공개 사이트는 백엔드에 의존하지 않는다
> (`ARCHITECTURE.md §1.3`). DB 상태는 `/actuator/health`로 사람이 확인한다.

#### ★ 2026-08-27 — 같은 누수가 **한 군데 더** 있었다 (커넥션 풀)

핑 경로를 옮겨 "HTTP 요청이 DB를 깨우는" 길은 막았다. 그런데 **커넥션 풀이
같은 일을 하고 있었다.** 핑과 무관하게, 서버가 깨어 있는 동안 계속.

HikariCP 6.3.3의 기본값 두 개가 겹친 결과다 (바이트코드로 확인 —
`DEFAULT_KEEPALIVE_TIME` · `HikariConfig.validateNumerics`):

| 기본값 | 실제 동작 |
|---|---|
| `keepaliveTime` = **2분** (0이 아니다) | 유휴 커넥션에 **2분마다 쿼리를 보낸다** |
| `minimumIdle` = `maximumPoolSize` (음수 → 보정) | 풀이 **고정 크기 3개**라 절대 비워지지 않는다 |

```
서버 기동 → 풀에 커넥션 3개 → 2분마다 keepalive 쿼리 → Neon 유휴 타이머 계속 초기화
        → 자동 정지가 한 번도 걸리지 않음 → 서버가 깨어 있는 558h/월 = Neon도 558h
```

`idleTimeout`(기본 10분)이 이걸 막아줄 것 같지만 아니다 — 고정 크기 풀에서는
HikariCP가 `"idleTimeout has been set but has no effect because the pool is
operating as a fixed size pool."`을 남기고 **무시한다.**

**고친 방법** (`application.yml`):

```yaml
spring.datasource.hikari:
  keepalive-time: 0      # ★ 커넥션 유지 핑을 끈다 — 이게 Neon을 깨우던 것
  minimum-idle: 0        # 풀을 0까지 비운다 (기본값은 고정 크기)
  idle-timeout: 240000   # 4분 — Neon 자동 정지(약 5분)보다 먼저 비운다
```

**부수 효과가 하나 더 있다 — 첫 쿼리 실패/지연이 사라진다.** 정지 후에 풀을
비우면 죽은 커넥션이 남아, 실제 사용자 요청의 첫 쿼리가 `검증 실패 → 폐기 →
재연결`을 거친다. 미리 비우면 그 경로 자체가 없다.

**사람이 기억하지 않게 고정했다** —
`backend/src/test/java/kr/light/config/DataSourcePoolConfigTest.java`가
`keepalive-time != 0`이나 `minimum-idle != 0`이면 CI에서 실패한다. `prod` 문서가
이 값을 되살리는 경우까지 본다. `HealthProbeTest`와 같은 성격의 장치다 —
**깨져도 아무 증상이 없기 때문에** 테스트가 유일한 감지 수단이다.

> ⚠️ **교훈**: "핑이 DB를 건드리지 않는다"만으로는 부족하다. **애플리케이션이
> 주기적으로 DB에 보내는 것이 또 없는지**를 봐야 한다. 앞으로 스케줄러
> (`@Scheduled` 배치 — 예: §3.6의 `PENDING` 사진 정리)를 추가할 때 같은 질문을
> 다시 해야 한다: **이게 Neon을 깨우는가?**

**저장 용량** 0.5GB는 메타데이터 전용이라 여유가 크다. 사진·파일은 R2에 있고
DB에는 경로와 메타만 들어간다.

### 3.3 Render — "상시 가동"이 오히려 서비스를 멈출 수 있다

750 인스턴스시간/월. **인스턴스가 깨어 있는 동안만** 시간이 소모된다(슬립 중에는
소모되지 않는다). 그래서 슬립 방지 핑의 스케줄이 곧 사용량이다.

| 핑 스케줄 | 월 사용 | 여유 | 대가 |
|---|---|---|---|
| 24시간 상시 | 744h (99.2%) | **6h** ⚠️ | 없음 |
| **06:00~24:00** ★ 채택 | **558h (74%)** | **192h** | 새벽 첫 방문자만 콜드스타트 |
| 서비스 2개를 24시간 | 1,488h | 초과 | — |

**24시간 상시를 택하지 않은 이유** — 여유 6시간이 안전하지 않다.
**배포할 때 Render가 새 인스턴스를 띄우고 기존 것을 내리는 동안 두 개가 잠깐
겹쳐 돈다.** 이 겹침이 쌓여 750을 넘기면, 카드가 없으므로 과금이 아니라
**서비스가 정지**된다 — **"상시"를 노린 설정이 월말에 서비스를 멈추게 하는** 셈이다.
배포 빈도가 높은 시기(지금)에는 특히 그렇다.

교회 사이트라 새벽 트래픽은 사실상 0이고, **06:00 핑이 사람들이 오기 전에 서버를
깨워둔다.** 실사용자가 콜드스타트를 겪을 일은 거의 없다.
(PM 결정 2026-08-27 · 스케줄 값은 `infra/render/README.md §1-⑥`)

**그래서 스테이징 서버를 둘 수 없다.** 비용 제약이 기능을 결정한 사례다.

- 메모리 512MB → `-Xmx400m` (`backend/Dockerfile`). 임의로 올리면 OOM으로 죽는다
- 무료 인스턴스는 결제 수단 없이 만들 수 있다 → 1차 차단 성립

### 3.4 Vercel — Hobby 플랜의 조건을 알아둘 것

FE는 Vercel Hobby(무료)에 올린다. 결제 수단 없이 쓸 수 있어 1차 차단이 성립한다.

⚠️ **Hobby 플랜은 상업적 사용을 허용하지 않는다.** 교회 홈페이지는 비상업으로
보는 것이 일반적이지만, **온라인 헌금·결제·광고가 붙는 순간 조건이 달라진다.**
그 기능을 검토할 때 이 항목을 함께 본다.

### 3.5 cron-job.org — ⏸️ **개발 단계에는 꺼둔다** (PM 결정 2026-08-27)

무료, 결제 개념 없음.

> ### ⏸️ 현재 상태: **꺼져 있다**
>
> 동작 검증은 끝났다(§7). **그리고 그 직후 의도적으로 껐다.**

> 월 558시간을 **"아무도 안 쓰는데 깨어 있는 상태"**로 소모한다. 개발 단계에
> 그럴 이유가 없고, Render 750시간/월 한도에 여유를 남겨두는 편이 낫다.

> ⚠️ **API 응답이 갑자기 느려 보이면 서버가 죽은 게 아니라 깨어나는 중이다.**

>

| 스케줄 | `*/10 6-23 * * *` (월 약 3,348회) |
| Timezone | **`Asia/Seoul`** — 기본값 UTC로 두면 주일 예배 시간에 슬립한다 |

> ### ⚠️ GitHub Actions의 `schedule`로 핑을 돌리면 안 된다
>
> "이미 Actions를 쓰는데 cron 하나 더 넣으면 되지"가 자연스러운 생각이지만,
> **Private 저장소는 Actions 실행이 무료 분에서 차감된다**(§3.1). 그리고
> **각 실행은 최소 1분으로 과금된다** — 10초짜리 curl도 1분으로 센다.
>
> | | |
> |---|---|
> | 10분 주기 × 18시간 | 월 약 3,348회 |
> | 최소 1분 과금 | **월 약 3,348분** |
> | 무료 한도 | **2,000분** |
>
> **한도를 1.7배 넘긴다.** CI가 멈추므로 배포도 함께 멈춘다. 핑처럼 자주·짧게
> 도는 작업은 **분 단위로 과금되지 않는 외부 무료 서비스**에 두는 것이 맞다.
> (Actions의 `schedule`은 저장소가 오래 비활성이면 자동으로 꺼지기도 한다.)

### 3.6 ⚠️ Cloudflare R2 — 1차 방어가 안 되는 유일한 후보 (M3)

`ARCHITECTURE.md §4`가 사진·주보 저장소로 R2를 채택했다. 근거는 타당하다 —
**전송량 무료**가 결정적이고, 사진 다운로드가 핵심 기능인 이 프로젝트에서
egress 과금이 있는 서비스는 쓸수록 비용이 오른다.

**그런데 R2는 무료 한도가 있어도 활성화에 결제 수단을 요구한다.** 즉:

- 1차 방어(**결제 수단 미등록**)가 **성립하지 않는다**
- Cloudflare에는 "지출 한도 $0" 같은 하드 스톱이 없다
- 따라서 한도를 넘기면 **중단이 아니라 실제 과금**이 된다 ($0.015/GB·월)

이건 §0.1의 "결제 수단을 요구하는 서비스는 채택하지 않는다"와 정면으로
충돌한다. **M3 착수 전에 PM이 결정해야 한다.**

**2차 가드는 이미 설계돼 있다** (`ARCHITECTURE.md §4.3`, `BACKEND_TASKS.md §91`):
- 원본 미보관 · 2560px 리사이즈 (10GB로 약 7,400장)
- 80% 경고 · **95%에서 업로드 차단** (`STORAGE_LIMIT` 409 — 구현됨)
- 삭제 시 R2 객체 동반 삭제 · `PENDING` 정리 배치

⚠️ **다만 저장 용량만 막고 있다.** R2는 **연산 횟수**(Class A 쓰기 1M/월 ·
Class B 읽기)에도 한도가 있는데, 지금 설계에 그걸 세는 장치가 없다. presigned URL
발급이 Class A에 해당하므로, 재시도 루프 같은 버그 하나로 조용히 늘어날 수 있다.

**선택지 (M3 결정)**

| 안 | 내용 | 문제 |
|---|---|---|
| A | R2를 쓰고 **2차 가드를 강화** (연산 횟수 카운터 추가 + 월 1회 대시보드 확인) | 1차 방어 없음 — 가드에 버그가 있으면 과금 |
| B | 결제 수단이 필요 없는 저장소로 변경 | 무료 용량이 작아진다(예: 1GB) → 사진첩 설계(§4.1)를 다시 짜야 한다 |
| C | 사진 원본 보관을 **사이트 밖**(구글 드라이브 등)에 두고 사이트는 썸네일만 | 다운로드 기능(핵심)이 약해진다 |

→ **아직 정하지 않았다.** M3 착수 전까지 미결로 남기고, 그때 이 표를 근거로
결정한다. **지금 R2 계정을 만들지 않는다** (`ARCHITECTURE.md §9`의 환경변수를
미리 넣지 않는 이유와 같다).

      이게 실제로 막혔다는 유일한 증거다

> ### ⚠️ Suspended 상태는 배포 성공과 구별되지 않는다
>
> Render 서비스를 정지(Suspend)시켜 두면 응답이 이렇게 온다:
>
> ```
> HTTP/1.1 503 Service Unavailable
> x-render-routing: suspend-by-user
> This service has been suspended by its owner.
> ```
>
> **그런데 Deploy Hook은 그대로 200을 반환한다.** 즉 GitHub Actions의 `deploy`
> 잡은 **초록불로 끝나고**, 배포는 "성공"으로 기록되는데 **서버는 아무 요청도
> 받지 않는다.** 훅 호출 성공은 "배포가 시작됐다"까지만 보증한다는 뜻이다.
>
> 그래서 배포 후 확인은 **훅 결과가 아니라 실제 응답**으로 한다:
> `curl -i https://light-homepage.onrender.com/actuator/health/alive` → `200 {"status":"UP"}`

> ⚠️ **"카드가 등록돼 있지 않다"가 이 설계의 전부다.** 나머지는 서비스가 멈추지
> 않게 하는 편의 장치다. 카드를 등록하는 순간 이 문서의 1차 방어가 사라진다.

> ### ⚠️ 메모리 경고선이 420MB인 이유 — `-Xmx400m`은 여유가 없다
>
> 힙 상한 400MB + 힙 밖 메모리(메타스페이스·코드캐시·스레드 스택) 약 180MB면
> **합계가 512MB를 넘는다.** 즉 힙이 실제로 400MB까지 차면 과금이 아니라
> `Exited with status 137`(OOM)로 죽는다. 지금 안 죽는 이유는 힙을 그만큼 쓰지
> 않아서일 뿐이다(2026-08-26 실측 총 299MB).
>
> 그래서 2026-08-27에 **힙 밖 메모리를 줄이는 쪽으로** 손봤다 —
> Tomcat 스레드 200→20(스택이 스레드마다 붙는다) · SerialGC 고정(G1은 힙 밖
> 보조 자료구조가 더 붙는다). **`-Xmx`는 건드리지 않았다** — 낮추면 M4의
> PDF→이미지 변환이 힙에서 막힌다.

경고선에 닿으면 **기능을 줄여서 맞춘다.** `WORKPLAN.md §1`이 "$0 제약, 기능
축소 없음 — 기간으로 조정"이라고 했으므로, 초과가 임박하면 **일정을 늦추는 것이
플랜을 올리는 것보다 먼저다.**
