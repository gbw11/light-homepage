## 2. 권한 모델 — 화면은 3파트, 내부 등급은 그대로 5개

PM이 말한 3파트는 **사용자에게 보이는 구분**이고, 내부 등급은 기존 5개를 유지하는
쪽을 권한다(관리 권한을 전도사에게만 두는 기존 구분이 여전히 필요하다).

| 파트 (사용자 관점) | 내부 role | 누구인가 | 할 수 있는 것 |
|---|---|---|---|
| **① 비로그인 새가족** | `GUEST` | 교회에 처음 온 사람 | 약도 · 예배 시간/장소 · 주차 안내 · 공개 공지 · 주보 · 설교 영상 · 새가족 등록 신청 |
| **② 로그인 회원** | `MEMBER` | 명단에 있는 교인 | ①의 전부 + **월례회 자료 열람** · **사진첩 열람·개별 다운로드** · 내 정보/비밀번호 · (❓ 내 출결 조회 `§9-E`) |
| **③ 임원 · 전도사** | `LEADER` / `PASTOR` | 임원, 전도사 | ②의 전부 + **월례회 자료 업로드** · **사진첩 업로드/삭제** · **출석부 작성** · **예산안 작성·수정·열람** · 주보 업로드 · 공지/회의록 작성 |
| (내부용) | `PENDING` | 명단 대조는 됐으나 미승인 | `§9-B` 결정에 따라 존재 여부가 갈린다 |

**`LEADER`와 `PASTOR`의 차이는 그대로 둔다**: 회원 관리(`/admin/members/*` — 승인·
역할 변경·비밀번호 초기화)는 **`PASTOR`만**. 임원이 임원을 임명할 수 있으면
권한 상승 경로가 생긴다.

## 4. ⚠️ 보안 검토 — "아이디=이름, 비밀번호=생년월일"을 그대로 만들면 안 된다

PM 구상의 **목적(명단에 있는 사람만 들어온다)은 맞다.** 다만 그 구현 형태를
그대로 두면 아래 셋이 깨진다. 대안은 목적을 유지하면서 이 셋만 막는다.

### 문제 ①: 이름은 유일하지 않다
동명이인이 한 명이라도 생기면 로그인 아이디가 충돌한다. 교회 규모에서 "김OO"가
둘일 확률은 낮지 않다. **아이디는 이름이 아니어야 한다.**

### 문제 ②: 생년월일은 비밀이 아니다
같은 교회 사람이면 이름·생년월일·전화번호를 대부분 안다. 즉 **"비밀번호=생년월일"
상태로 남아 있는 계정은 아는 사람이면 누구나 열 수 있다.** 그리고 그 상태는
"본인이 바꿀 때까지" 지속된다 — 실제로는 상당수가 안 바꾼다.

### 문제 ③: 대조 엔드포인트가 명단 조회기가 된다
이름+생년월일을 반복 요청하면 **누가 우리 교회 교인인지 외부에서 확인할 수 있다.**
"생년월일이 틀렸습니다" 같은 친절한 오류는 이걸 더 쉽게 만든다.

### ✅ 권장 대안 — 목적은 같고 위 셋이 없다

```
[최초 1회]  이름 + 생년월일 + 전화번호  →  명단 대조 (3개 전부 일치해야 통과)
                     ↓ 통과
            그 자리에서 로그인 아이디 + 비밀번호를 "직접 설정"
                     ↑ 임시 비밀번호 상태를 아예 만들지 않는다
                     ↓
            (❓§9-B) 임원 승인 대기  or  즉시 MEMBER
[이후]      설정한 아이디 + 비밀번호로 로그인
```

핵심 차이는 하나다. **"생년월일로 로그인한 뒤 나중에 바꾼다"가 아니라,
"생년월일은 대조에만 쓰고 로그인 자격은 처음부터 본인이 만든다".**
생년월일이 유효한 비밀번호였던 시간이 **0초**가 된다. 사용자 경험은 거의 같다 —
어차피 첫 로그인 때 이름·생년월일·전화번호를 입력하는 것은 동일하다.

함께 지켜야 할 것:

- **로그인 아이디**: 이름 금지. **전화번호**를 쓰거나(명단에 있고 유일하고 본인이
  외운다) 사용자가 직접 정한 아이디를 쓴다 → ❓`§9-A`
- **대조 응답은 성공/실패 두 가지만.** 어떤 필드가 틀렸는지 알려주지 않는다
- **대조 엔드포인트에 rate limit**: IP당 분당 5회, 동일 이름 10회 실패 시 15분 잠금.
  이게 없으면 문제 ③이 그대로 남는다
- **대조 결과가 2건 이상이면 거부**하고 "임원에게 문의" 안내 (동명이인 + 같은 생일)
- **이미 계정이 만들어진 명단 행은 재대조 불가** (`claimed_at`이 있으면 즉시 실패).
  한 사람 명단으로 두 계정이 생기면 안 된다
- 비밀번호는 **BCrypt 해시**. 생년월일은 명단 테이블에만 두고 **비밀번호로 저장하지
  않는다**

## 5. 로그인 플로우 상세

### 5.1 명단 대조 — `POST /api/auth/verify-roster`
권한 `G`

```json
// 요청
{ "name": "김OO", "birthDate": "2001-03-14", "phone": "010-1234-5678" }
```
```json
// 200 — 대조 성공. 5분 유효한 1회용 등록 토큰을 발급한다
{ "data": { "registrationToken": "eyJ...", "name": "김OO", "expiresIn": 300 } }
```

| 실패 | code | 응답 메시지 |
|---|---|---|
| 불일치 / 명단에 없음 / 이미 계정 있음 | `UNAUTHORIZED` | **전부 동일한 문구** ("명단에서 확인되지 않습니다") |
| 동명이인 2건 이상 | `VALIDATION_ERROR` | "임원에게 문의해 주세요" |
| rate limit 초과 | `UNAUTHORIZED` | 동일 문구 (429를 따로 쓰면 잠금 사실이 노출됨 — ❓`§9-G`) |

**정규화 규칙** (대조 전에 양쪽 모두 적용):
- 전화번호: 숫자만 남김 (`010-1234-5678` → `01012345678`)
- 이름: 앞뒤·중간 공백 제거
- 생년월일: `YYYY-MM-DD`. 엑셀에 `2001.03.14` / `010314` 등이 섞여 있으면
  **임포트 시점에 정규화**한다 (`§6.3`)

### 5.2 계정 생성 — `POST /api/auth/register`
권한 `G` (`registrationToken` 필요)

```json
// 요청
{ "registrationToken": "eyJ...", "loginId": "01012345678", "password": "새비밀번호12!" }
```
```json
// 201
{ "data": { "id": "42", "name": "김OO", "role": "PENDING" } }
```
- 토큰은 **1회용**이며 소비 즉시 폐기. 만료(5분) 시 `UNAUTHORIZED`
- 명단 행에 `claimed_at`, `member_id`를 기록 (재사용 차단)
- 비밀번호 정책: 8자 이상. **생년월일·전화번호와 같으면 거부** (`VALIDATION_ERROR`)

### 5.3 로그인 — `POST /api/auth/login` (기존 `§2.2` 교체)
```json
// 요청
{ "loginId": "01012345678", "password": "..." }
```
응답 형태는 기존과 동일(`id` `name` `village` `role`). 쿠키 정책도 그대로
(`§1.4` — httpOnly, access 30분 / refresh 14일).
**로그인 실패 5회 시 15분 잠금.**

`§2.12` 비밀번호 변경(`POST /auth/password/change`)은 **그대로 유지**된다 —
본인이 언제든 바꿀 수 있어야 한다는 PM 요구는 이걸로 충족된다.

### 5.4 ⚠️ 비밀번호를 잊었을 때 — `POST /api/admin/members/{id}/password/reset`
권한 `T` (❓`§9-C`로 `L`까지 열지 결정)

이메일을 안 받으므로 **자동 재설정 경로가 없다.** 임원/전도사가 대신 초기화한다.

```json
// 200 — 1회용 임시 코드를 화면에 표시해 본인에게 구두/문자로 전달
{ "data": { "resetCode": "8H2K-9QX1", "expiresAt": "2026-08-28T05:00:00Z" } }
```
- 이 코드로 `POST /api/auth/password/reset-with-code`를 호출해 **본인이 새 비밀번호를
  설정**한다. 임원이 비밀번호를 정해서 알려주는 방식은 만들지 않는다
- 코드는 **1회용 · 30분 만료 · 해시로 저장**
- 초기화 이력을 남긴다 (누가 누구 계정을 초기화했는지)

## 6. 데이터 모델

### 6.1 `member_roster` — 엑셀 명단 (계정과 분리)

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | bigint PK | |
| `name` | varchar(50) | |
| `birth_date` | date | |
| `phone_norm` | varchar(20) | **숫자만.** 대조·인덱스는 이 컬럼으로 |
| `village` | varchar(10) | 마을 |
| `position` | varchar(30) | 직분(임원 여부 판단 근거) — nullable |
| `active` | boolean | 이탈 교인은 `false` → 대조 대상에서 제외 |
| `claimed_at` | timestamp | nullable. 계정 생성 시각 |
| `member_id` | bigint FK | nullable unique. 만들어진 계정 |

**인덱스**: `(name, birth_date, phone_norm)` — 대조 쿼리 전용.

**명단과 계정을 한 테이블에 합치지 않는다.** 명단은 교회가 관리하는 사실이고
계정은 그 사람이 만든 것이다. 합치면 "계정 없는 교인"을 표현할 수 없고
(→ `§7` 출석부가 성립하지 않는다), 탈퇴 시 명단까지 사라진다.

### 6.2 `member` — 계정 (기존 테이블 수정)

| 컬럼 | 변경 |
|---|---|
| `email` | **nullable로 완화** (또는 제거 — ❓`§9-F`) |
| `login_id` | **신규** varchar(50) unique not null |
| `password_hash` | 유지 (BCrypt) |
| `roster_id` | **신규** FK unique — 어느 명단 행에서 만들어졌는지 |
| `role` | `GUEST` 제외 4개 |
| `failed_login_count` · `locked_until` | **신규** (`§5.3` 잠금) |
| `kakao_id` | ❓`§9-F` |

### 6.3 엑셀 → DB 임포트

권장: **엑셀을 CSV로 저장해 초기 시드 스크립트로 넣는다.** 관리 화면에서 xlsx를
파싱하는 기능은 이번 범위에서 빼자 — 라이브러리·검증 비용 대비 쓰는 횟수가 적다
(❓`§9-C`에서 재확인).

임포트 시 반드시 할 것:
1. 위 정규화 규칙 적용 (전화번호 숫자만, 생년월일 `YYYY-MM-DD`)
2. **`(name, birth_date, phone_norm)` 중복 행 리포트** — 중복이 있으면 그 사람은
   영영 대조에 실패한다(`§5.1` 2건 이상 거부). 임포트 시점에 잡아야 한다
3. **필수값 누락 행 리포트** — 전화번호 없는 교인이 실제로 있을 것이다 → `§9-A`

⚠️ **명단 원본 엑셀·CSV를 저장소에 커밋하지 않는다.** 실명·생년월일·전화번호가
담긴 개인정보 파일이다 (`.gitignore` 확인, 시크릿 스캔 액션 대상).

## 7. 신규 기능: 출석부 — **기존 스펙에 아예 없다**

`SPEC_API.md`·`SPEC_FUNCTIONAL.md`·`WIREFRAME.md` 어디에도 출석부가 없다.
아래는 초안이고 FE 화면도 아직 없다. **`§9-E` 결정 후 별도 브리핑으로 확정한다.**

| 엔드포인트 | 권한 | 설명 |
|---|---|---|
| `GET /api/attendance/sessions?from=&to=&page=` | `L` | 출석 회차 목록 |
| `POST /api/attendance/sessions` | `L` | 회차 생성 `{ "date": "2026-08-30", "type": "SUNDAY_SERVICE", "title": "주일예배" }` |
| `GET /api/attendance/sessions/{id}` | `L` | 회차 + 전 교인 출결 상태 (명단 기준) |
| `PUT /api/attendance/sessions/{id}/entries` | `L` | 출결 일괄 저장 `[{ "rosterId": "12", "status": "PRESENT" }]` |
| `DELETE /api/attendance/sessions/{id}` | `L` | 회차 삭제 |
| `GET /api/attendance/me?from=&to=` | `M` | **내 출결만** (❓`§9-E`) |
| `GET /api/attendance/stats?village=&from=&to=` | `L` | 마을별 집계 |

- `status` enum: `PRESENT` · `LATE` · `ABSENT` · `EXCUSED`
- **출결 대상은 `member`가 아니라 `member_roster`다.** 계정을 안 만든 교인도
  출석은 체크해야 한다 — 명단/계정을 분리하는 두 번째 이유다
- `PUT`은 **전체 교체가 아니라 upsert**로. 두 임원이 동시에 다른 마을을 체크하면
  전체 교체는 서로를 덮어쓴다
- ⚠️ **출석 데이터는 "누가 교회에 안 나왔는지"의 기록이다.** 예산안과 같은 급의
  민감 정보로 다룬다 — 목록 응답에 불필요한 개인정보(전화번호 등)를 싣지 않는다

## 10. 착수 순서 (확정 후)

1. `member_roster` 스키마 + CSV 임포트 스크립트 + **중복/누락 리포트**
2. `POST /auth/verify-roster` + rate limit + `POST /auth/register`
3. `POST /auth/login` 교체 (`loginId` 기반) + 실패 잠금
4. **`BACKEND_TASKS.md §6` 인가 테스트 매트릭스를 `§3` 값으로 먼저 고치고** 테스트 작성
5. `§3` 매트릭스대로 사진첩·월례회 권한 되돌리기
6. 관리자 비밀번호 초기화(`§5.4`)
7. 출석부 (`§7` — 별도 브리핑 확정 후)

**4번이 5번보다 앞이다.** 매트릭스를 안 고치고 권한을 바꾸면 잘못된 기준으로
테스트가 "통과"한다 — 2026-08-26에 실제로 있었던 일이다.
