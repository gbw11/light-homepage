### 2. 권한 — 화면은 3파트, 내부 role은 기존 5개 유지

| 파트 | role | 할 수 있는 것 |
|---|---|---|
| 비로그인 새가족 | GUEST | 약도·예배시간/장소·주차·공개공지·주보·설교·새가족등록 |
| 로그인 회원 | MEMBER | + 월례회 열람, 사진첩 열람·개별다운, 내 정보/비번 |
| 임원·전도사 | LEADER/PASTOR | + 월례회 업로드, 사진첩 업로드/삭제, **출석부 작성**, 예산안 작성·수정·열람, 주보·공지·회의록 |

**회원 관리(승인·역할변경·비번초기화)는 PASTOR만** 유지합니다. 임원이 임원을 임명할 수 있으면 권한 상승 경로가 생깁니다.

### 3. ⚠️ "아이디=이름 / 비번=생년월일"은 그대로 만들면 안 됩니다

목적(명단에 있는 사람만 들어온다)은 맞는데, 그 형태 그대로면 셋이 깨집니다.
1. **이름은 유일하지 않다** — 동명이인 하나면 아이디가 충돌
2. **생년월일은 비밀이 아니다** — 같은 교회 사람은 이름·생일·전번을 대부분 안다. 그 상태가 "본인이 바꿀 때까지" 계속되는데, 실제로는 상당수가 안 바꿈
3. **대조 API가 명단 조회기가 된다** — 반복 요청으로 "누가 교인인지" 확인 가능

**✅ 대안 (목적 동일, 위 셋 없음)**
```
[최초 1회] 이름+생년월일+전화번호 → 명단 대조 (3개 전부 일치)
            ↓ 통과 즉시
           로그인 아이디 + 비밀번호를 본인이 직접 설정  ← 임시비번 상태를 아예 안 만듦
            ↓
           (❓B) 임원 승인 대기 or 즉시 MEMBER
[이후]     설정한 아이디+비번으로 로그인
```
차이는 하나입니다. **"생년월일로 로그인 후 나중에 변경"이 아니라 "생년월일은 대조용으로만, 로그인 자격은 처음부터 본인이 생성".** 생년월일이 유효한 비밀번호였던 시간이 **0초**가 됩니다. 사용자가 입력하는 정보는 원안과 똑같습니다.

함께 필요한 것:
- 로그인 아이디는 **전화번호** 권장 (이름 금지) ❓결정 A
- **대조 응답은 성공/실패 두 가지만** — 어느 필드가 틀렸는지 알려주지 않음
- **rate limit**: IP당 분당 5회, 동일 이름 10회 실패 시 15분 잠금
- 대조 결과 **2건 이상이면 거부** → "임원에게 문의"
- **이미 계정 있는 명단 행은 재대조 불가** (`claimed_at`)
- BCrypt. **생년월일을 비밀번호로 저장하지 않음**

### 4. 새 API

| 엔드포인트 | 권한 | 설명 |
|---|---|---|
| `POST /api/auth/verify-roster` | G | `{name, birthDate, phone}` → 5분짜리 1회용 `registrationToken` |
| `POST /api/auth/register` | G | `{registrationToken, loginId, password}` → 계정 생성 |
| `POST /api/auth/login` | G | `{loginId, password}` (기존 email 방식 교체). **실패 5회 15분 잠금** |
| `POST /api/admin/members/{id}/password/reset` | T | 1회용 리셋 코드 발급 (30분, 해시 저장). 임원이 비번을 정해주는 방식 아님 |
| `POST /api/auth/password/reset-with-code` | G | 코드로 본인이 새 비번 설정 |

`§2.12` 비밀번호 변경은 그대로 유지 — 본인이 언제든 바꿀 수 있습니다.
쿠키 정책(`§1.4` httpOnly / access 30분 / refresh 14일)도 그대로입니다.

### 5. DB — 명단과 계정을 **분리**합니다

`member_roster`: `id, name, birth_date, phone_norm(숫자만), village, position, active, claimed_at, member_id`
→ 인덱스 `(name, birth_date, phone_norm)`

`member` 수정: `login_id` unique 추가 · `roster_id` FK unique 추가 · `email` nullable · `failed_login_count`/`locked_until` 추가

**합치면 안 되는 이유**: "계정 안 만든 교인"을 표현 못 하고, 그러면 **출석부가 성립하지 않습니다**(출결 대상은 member가 아니라 roster).

**엑셀 임포트**: xlsx 파싱 기능 대신 **CSV 시드 스크립트** 권장. 임포트 시 ①정규화(전번 숫자만, 생일 YYYY-MM-DD) ②**중복 행 리포트**(중복이면 그 사람은 영영 대조 실패) ③필수값 누락 리포트.
⚠️ **명단 원본 파일은 절대 저장소에 커밋하지 않습니다.**

### 6. 출석부 — 기존 스펙에 아예 없습니다 (초안)

`GET/POST /api/attendance/sessions` · `GET /sessions/{id}` · `PUT /sessions/{id}/entries` · `GET /stats` (전부 L)
status: `PRESENT|LATE|ABSENT|EXCUSED` · 대상은 **roster** · `PUT`은 전체교체 아니라 **upsert**(두 임원 동시 작성 시 서로 덮어씀)
※ 출결은 "누가 안 나왔는지"의 기록 — 예산안급 민감 정보로 다룹니다.

### 7. ❓ 결정 필요 7건 (이거 답 주시면 착수 가능)

**A. 로그인 아이디** — ①전화번호(권장) ②직접 정한 아이디 ③이름(원안, 동명이인에서 깨짐)
**B. 대조 통과 후** — ①즉시 MEMBER ②PENDING→임원 승인 **(권장 ②, 기존 승인 큐 재사용)**
**C. 비번 초기화 권한** — ①PASTOR만(권장) ②임원까지
**D. 내부공지·회의록도 닫나** — ①닫음(위 표는 이 가정) ②공개 유지
**E. 출석부 범위** — 본인이 자기 출결 조회 가능? 임원은 전체 vs 마을만? (1차는 "본인조회 없음+임원 전체" 권장)
**F. 카카오** — ①폐기(권장) ②보류
**G. rate limit 초과 응답** — 일반 실패와 동일 권장(로그에서만 구분)

### 8. 착수 순서 (확정 후)

1. `member_roster` 스키마 + CSV 임포트 + 중복/누락 리포트
2. `verify-roster` + rate limit → `register`
3. `login` 교체 + 실패 잠금
4. **`BACKEND_TASKS.md §6` 인가 테스트 매트릭스 먼저 수정** ← 5번보다 앞
5. 사진첩·월례회 권한 되돌리기
6. 관리자 비번 초기화
7. 출석부 (별도 브리핑 후)

**4번이 5번보다 앞인 이유**: 매트릭스를 안 고치고 권한을 바꾸면 잘못된 기준으로 테스트가 "통과"합니다. 8/26에 실제로 있었던 일입니다.
