# 관측 · 신뢰성 · 피드백 (Module 6)

실행이 잘 됐는지 나중에 **누가 봐도 알 수 있게** 기록하는 방법과, 실패를
개선으로 이어지게 하는 절차.

---

## 1. 무엇을, 어디에 기록하는가

| 기록 | 위치 | 내용 |
|---|---|---|
| 단계별 기록 (커밋) | git 커밋 로그 | `WORKFLOW.md` 단위 하나 = 커밋 하나. 커밋 메시지에 "무엇을/왜"를 남긴다 |
| 실행 로그 | PR 본문 | 로컬에서 돌린 검증 결과(lint/type-check/build 통과 여부), 스크린샷 |
| 판단 기록 | 커밋 메시지 또는 PR 본문 | `HARNESS.md` §1의 "요청 → 작업 명세"에서 정리한 판단 근거 |
| 트러블슈팅/사고 기록 | 관련 문서의 별도 섹션 (예: `infra/jenkins/README.md` §6) | 재발 방지가 필요한 문제는 문서에 영구 기록. 대화 기록에만 남기지 않는다 |
| 장기 컨텍스트(팀 결정, 진행 상태) | Claude 메모리(`MEMORY.md` 및 연결 문서) | 세션이 끝나도 유지해야 하는 결정사항 |

**측정값(있으면 남길 것)**: lint 경고 수, 타입 에러 수, 빌드 시간, CI
소요 시간 — 급격히 나빠지면 그 시점의 변경을 의심한다.

---

## 2. 실패 허용 범위

- **같은 단위에서 검증 루프(`WORKFLOW.md` §2)가 2회 연속 실패**하면, 3번째
  시도를 그냥 반복하지 않는다. 원인을 다시 진단하거나, 원인을 모르겠으면
  사용자에게 알린다 (무한 재시도 금지).
- CI(Jenkins/Actions)가 **한 브랜치에서 연속 실패**하면 그 원인이 코드가
  아니라 인프라(Jenkins 설정 등)일 가능성을 먼저 배제한다 — 오늘 겪은
  `.env.example` 오탐, `node22` 툴 누락, `server_develop` 삭제 사고가 전부
  이 케이스였다 (`infra/jenkins/README.md` §6 참고).

## 3. 최초 실패 지점 분석

실패를 발견하면 **가장 최근에 통과했던 검증 지점**부터 되짚는다 — 마지막
성공 커밋 이후 무엇이 바뀌었는지가 원인의 대부분이다.

```
마지막으로 성공한 단위(커밋) 확인
  → 그 다음 단위에서 무엇을 바꿨는지 diff 확인
  → 그 변경이 실패와 연결되는지 확인
  → (연결 안 되면) 환경 문제(Jenkins/의존성 버전 등)를 의심
```

## 4. 장애 사례 → 개선으로 연결

문제를 고친 뒤 "고쳤다"에서 끝내지 않고, **같은 문제가 재발하지 않도록**
아래 중 하나로 남긴다:
- 문서에 트러블슈팅 섹션 추가 (예: 이 저장소의 `infra/jenkins/README.md §6`)
- 재발 가능성이 높으면 `HARNESS.md`/`PERMISSIONS.md`의 규칙으로 승격
  (예: "영구 브랜치는 PR head로 쓰지 않는다"류의 사고 방지 규칙)

이 저장소에서 이미 있었던 사례(참고용):
- Jenkins 플러그인 설치 미러 타임아웃 → `jenkins-plugin-cli` 우회로 해결,
  절차를 문서화 (`infra/jenkins/README.md §6.1`)
- `.env.example`이 Secret Scan에 오탐 → 정규식 예외 추가, PR로 반영
- GitHub "Automatically delete head branches" 설정이 영구 브랜치를
  삭제 → 설정 해제 + 브랜치 복구, 재발 방지 규칙을 `PERMISSIONS.md §3`에 기록
