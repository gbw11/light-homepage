# 프론트엔드 하네스 — 전체 설계

이 문서는 "하네스 엔지니어링" 커리큘럼(Module 1~7)을 이 프로젝트에 실제로
매핑한 결과다. 각 모듈이 이 저장소에서 **어떤 문서/규칙/도구**로 구현됐는지
찾아가는 지도 역할을 한다. 실행 절차 자체는 다른 문서에 있으니 여기서
중복하지 않는다.

| Module | 핵심 질문 | 이 프로젝트에서의 구현 |
|---|---|---|
| 1. Agent와 최소 실행 체계 | 에이전트가 필요한 일인가? | 본 문서 §1 |
| 2. 문맥 정보와 실행 구조 | 어떤 문서를 언제 읽는가? 언제 멈추는가? | [`WORKFLOW.md`](WORKFLOW.md) §1~2, §4 |
| 3. 안전한 도구 실행과 권한 제어 | 무엇을 승인 없이 해도 되는가? | [`PERMISSIONS.md`](PERMISSIONS.md) |
| 4. 실행 상태/기록/복구 | 중단되면 어디서부터 다시 시작하나? | [`WORKFLOW.md`](WORKFLOW.md) §3, §6 |
| 5. 검증/평가/배포 검토 | "됐다"를 뭘로 증명하나? | 본 문서 §2 |
| 6. 관측/신뢰성/피드백 | 실패는 어떻게 기록·개선되나? | [`OBSERVABILITY.md`](OBSERVABILITY.md) |
| 7. 목적별 최소 Harness | 지금 어느 자율성 단계인가? | 본 문서 §3 |

## 1. Agent가 필요한 일 vs 그냥 하면 되는 일 (Module 1)

모든 프론트엔드 요청에 `WORKFLOW.md`의 전체 루프(쪼개기 → 검증 → 커밋)를
적용하지 않는다. 먼저 판단한다:

| 유형 | 예 | 처리 방식 |
|---|---|---|
| **일반 자동화로 충분** | 오타 수정, 포맷팅, 이미 있는 컴포넌트에 prop 하나 추가 | 바로 수정. 하네스 루프 불필요 (단, lint/type-check는 여전히 돌린다) |
| **에이전트 판단이 필요** | 새 페이지, 새 API 연동, 상태 관리 설계, 스펙이 모호한 기능 | `WORKFLOW.md` 전체 루프 적용 |
| **판단 불가 — PM 확인 필요** | `SPEC_FUNCTIONAL.md`/`WIREFRAME.md`와 요청이 충돌, 백엔드 계약 미확정 | 구현하지 않고 먼저 질문 (§2 "판단 기록" 참고) |

**요청 → 작업 명세 변환**: 애매한 요청("게시판 페이지 만들어줘")을 받으면
바로 코드로 들어가지 않고, 아래를 먼저 명시적으로 정리한다 (말로 정리하고
사용자 확인을 받거나, 최소한 커밋 메시지/PR 본문에 남긴다):

```
요청: <원문>
작업 명세:
  - 무엇을 만드는가 (화면/기능 범위)
  - 참고 스펙 (SPEC_FUNCTIONAL.md §, WIREFRAME.md §)
  - 품질 기준 (WORKFLOW.md §2 루프 통과 + 접근성/반응형 등 COMPONENTS.md §4~5)
  - 이번에 다루지 않는 것 (스코프 밖)
판단 기록: <위 표에서 어느 유형으로 분류했는지, 왜>
```

수정 없이 그대로 로그(커밋 메시지 또는 PR 설명)에 남기는 것이 이 단계의
실습 핵심이다 — 나중에 "왜 이렇게 판단했는지" 추적 가능해야 한다.

### 1.1 자동 기록 — PM 결정 · 백엔드 인계

작업 중 아래 두 가지가 생기면, **요청받지 않아도 항상** 해당 파일에 적는다
(사람이 매번 "기록해줘"라고 말하게 만들지 않는다).

| 무엇이 생겼을 때 | 어디에 | 기준 |
|---|---|---|
| PM이 스펙을 확정·변경하는 말을 함 (기능·화면·정책 결정) | [`../../docs/DECISIONS.md`](../../docs/DECISIONS.md) | 그 문서 상단 형식 그대로 |
| 백엔드가 알아야 할 내용이 생김 (mock으로 확정한 API 계약, 새 라우트, 인가 매트릭스 추가 행 등) | [`../../docs/BACKEND_HANDOFF.md`](../../docs/BACKEND_HANDOFF.md) | 그 문서 상단 "언제 여기에 기록하는가" 기준 (`WORKFLOW.md` §7) |

두 문서 모두 **기록은 자동, 실제 전달(백엔드 담당자에게 알리기 등)은 PM
판단**이라는 원칙은 같다 — 이 저장소가 기록과 전달을 분리하는 방식이다.

## 2. 검증(Verification) vs 평가(Evaluation) (Module 5)

**검증** = 자동으로 참/거짓을 판정할 수 있는 것. **평가** = 사람(PM)의 판단이
필요한 것. 둘을 섞지 않는다.

| | 검증 (자동) | 평가 (사람) |
|---|---|---|
| 무엇을 확인하는가 | 코드가 깨지지 않았는가 | 이게 원하던 결과인가 |
| 도구 | `npm run lint`, `npm run type-check`, `npm run build`, Jenkins/Actions CI | PM이 브라우저로 직접 보고 판단 |
| 통과 기준 | 명령이 성공 종료(exit 0)했는가 | 화면이 스펙/의도에 맞는가 |

**규칙 — 명세 기반 개발(SDD):**
- "구현했습니다"라는 **에이전트의 말은 증거가 아니다.** 실제 명령 실행 결과
  (터미널 출력, CI 상태, 스크린샷)만 증거로 인정한다.
- 기능을 시작하기 전에 완료 기준(=작업 명세의 "품질 기준")을 먼저 적어두고,
  끝난 뒤 그 기준과 **실행 결과**를 대조한다 — 사후에 "그럴듯해 보이니 통과"로
  판단하지 않는다.
- 배포(머지) 가능 여부는 **검증(CI green)이 필수 조건**이고, **평가(PM 확인)**
  가 추가 조건이다. 검증만 통과했다고 자동으로 머지하지 않는다 (`CICD.md §4`
  머지 게이트와 동일한 원칙).

## 3. 이 프로젝트의 자율성 단계 (Module 7)

지금 프론트엔드 작업은 **아래 중 어느 단계에 있는지 항상 명확히 인지한다.**
단계를 건너뛰어 자율적으로 확장하지 않는다 — 확장은 사용자가 명시적으로
승인할 때만 일어난다.

| 단계 | 범위 | 승인 필요 여부 |
|---|---|---|
| **0. 관찰/읽기 전용** | 코드 탐색, 문서 읽기, 질문 답변, 계획 제시 | 불필요 |
| **1. 승인된 수정** *(현재 기본값)* | `frontend/**` 안에서 `WORKFLOW.md` 루프대로 단위 구현 → 로컬 커밋까지는 자동, **push/PR은 매번 보고 후 진행** | 단위별 결과 보고, push 전 확인 |
| **2. 자율 확장** | 동일 패턴이 반복되는 여러 단위(예: 비슷한 CRUD 페이지 여러 개)를 사용자가 명시적으로 위임하면, 여러 단위를 연속으로 진행 — 단, push는 여전히 개별 보고 | 사용자가 "이 패턴은 알아서 진행해도 됨"이라고 명시할 때만 |
| **3. 배포까지 자동** | main 배포 트리거까지 포함 | 이 프로젝트에서는 적용하지 않음 — 배포는 항상 사람이 머지 |

**단계적 도입 계획:**
1. 지금부터 몇 개 기능을 **Level 1**로 완료 (하네스 루프가 실제로 잘 도는지
   검증하는 기간)
2. 반복 패턴이 뚜렷해지고 신뢰가 쌓이면, 사용자가 특정 작업 유형에 한해
   **Level 2**로 전환 승인
3. **Level 3(배포 자동화)는 도입하지 않는다** — `docs/CICD.md`의 머지
   게이트 정책과 상충하기 때문 (사람이 최종 승인해야 하는 지점을 항상 둔다)

## 4. 병렬 작업 (git worktree)

여러 기능 단위를 **동시에** 진행할 때의 규칙. 순차 진행(§3 Level 1/2)과는
별개 축이다 — 병렬이어도 단위마다 `WORKFLOW.md` 루프(구현→lint→type-check→
눈으로 확인→커밋)는 그대로 각자 지킨다.

### 4.1 병렬화 가능 여부 판단 기준

**기준은 "수정할 파일이 겹치는가" 하나다.**

| 조건 | 처리 |
|---|---|
| 각 단위가 **새 라우트 폴더**만 만들고, 공용 파일(`lib/api/**`, `components/layout/**` 등)을 건드리지 않음 | ✅ 병렬 가능 |
| 두 단위가 같은 공용 파일(예: `lib/api/mock.ts`, `types.ts`)에 **새 항목을 추가**해야 함 | ⚠️ 원칙적으로 순차 진행. 병렬로 돌려야 한다면 각자 다른 함수/키에만 추가하도록 명시적으로 분리 지시 |
| 두 단위가 같은 파일의 **같은 부분**을 수정해야 함(예: `Header.tsx` 네비게이션에 항목 추가) | ✕ 병렬 금지 — 순차로 진행 |

판단은 작업을 쪼개는 시점(에이전트 또는 PM)에서 내리고, 왜 그렇게 나눴는지
PR 본문이나 커밋 메시지에 남긴다 (§1의 "판단 기록"과 동일한 원칙).

### 4.2 실행 방법 — 격리된 worktree

같은 작업 디렉터리에서 여러 단위를 동시에 건드리면 서로의 미완성 상태를
밟는다. 그래서 병렬 단위는 **각자 별도의 git worktree**에서 진행한다.

```
1. 베이스 브랜치(보통 frontend_develop)를 최신으로 동기화
2. 병렬 단위마다: 격리된 worktree + feat/fe-<slug> 브랜치 생성
3. 각 worktree 안에서 독립적으로 npm install → 구현 → lint/type-check →
   (헤드리스 환경이면) dev 서버 기동 후 curl로 렌더 확인 → 커밋
4. 각자 origin에 push → frontend_develop 대상 PR 생성
5. Jenkins/GitHub Actions CI가 ✅면 그 PR을 frontend_develop에 머지
   (CI가 ❌면 머지하지 않는다 — `CICD.md §4`와 동일한 게이트)
6. 다음 병렬 배치는 방금 머지된 frontend_develop을 새 베이스로 다시 동기화하고
   시작한다 — 오래된 베이스 위에서 계속 쌓지 않는다
```

### 4.3 주의사항

- 병렬 단위 수는 **한 번에 감당 가능한 범위**로 제한한다 — 리뷰·머지를
  추적할 수 있는 만큼만 (기준 없이 무한정 늘리지 않는다)
- 각 worktree는 독립된 `node_modules`가 필요하다 (git worktree는 코드만
  공유하고 설치된 패키지는 공유하지 않는다) — 병렬 단위 수만큼 설치 시간·
  디스크가 든다는 점을 감안한다
- 병렬 배치가 끝나고 병합까지 마친 뒤에야, 그 결과 위에 의존하는 다음 단위
  (예: 여러 페이지가 다 있어야 의미 있는 사이트맵·네비게이션 마무리 작업)를
  시작한다 — 병합 전 상태 위에 쌓지 않는다
