# 프론트엔드 작업 워크플로우 — 하네스 엔지니어링 루프

이 저장소의 프론트엔드 작업은 전부 이 방식으로 진행한다. 핵심은 두 가지뿐이다:
**① 작업을 눈에 보이는 최소 단위로 쪼갠다. ② 단위마다 검증을 통과해야 다음 단위로 넘어간다.**
검증되지 않은 코드 위에 다음 코드를 쌓지 않는다.

---

## 1. 작업 쪼개기

하나의 "단위"는 **화면에서 눈으로 확인 가능한 최소 변화**다. 기능 전체를 한 번에
구현하지 않는다.

**분해 기준 (기능 하나를 이 순서로 쪼개는 게 기본형):**
1. 레이아웃 뼈대 (정적 마크업, 데이터 없음)
2. 정적/더미 데이터로 렌더 (props로 하드코딩한 값 하나 흘려보기)
3. `@/lib/api` mock 연동 (실제 데이터 흐름, `NEXT_PUBLIC_USE_MOCK=1`)
4. 로딩 / 빈 상태 / 에러 상태
5. 인터랙션 (클릭, 폼 제출, 페이지네이션 등)
6. 접근성 확인 (키보드 포커스, 반응형)

모든 기능이 이 6단계를 다 거치는 건 아니다 — 예: 정적 페이지는 1~2단계로 끝난다.
**기준은 "이 커밋 하나가 30~60분 안에 끝날 만큼 작은가"**다. 안 그러면 더 쪼갠다.

각 단위는 **별도 커밋**으로 남긴다. 커밋 로그가 작업을 어떻게 쪼갰는지 그대로
보여줘야 한다.

---

## 2. 단위별 검증 루프 (순서 고정, 스킵 금지)

```
구현 → lint → type-check → 화면에서 눈으로 확인 → (통과) → 커밋 → 다음 단위
                                              → (실패) → 이 단위 안에서 고친다
```

```bash
npm run lint          # ESLint
npm run type-check    # next typegen && tsc --noEmit
npm run dev           # 브라우저에서 직접 렌더 확인 (mock 모드 기본)
```

- **세 개 다 통과하기 전에는 절대 다음 단위로 넘어가지 않는다.** "나중에 고치기"는
  없다 — 다음 단위가 이 단위 위에 쌓이는 순간 실패 원인을 찾기가 기하급수적으로
  어려워진다.
- 화면 확인은 텍스트로 "구현했다"고 끝내지 않는다. 실제로 `npm run dev`를 띄워서
  브라우저로 본다. 이미지/컴포넌트가 있으면 스크린샷으로 남긴다.

---

## 3. 커밋 / 푸시 기준

| 단계 | 행동 |
|---|---|
| 단위 하나 완료 (검증 통과) | 그 자리에서 커밋 |
| 기능 전체(여러 단위) 완료 | [`../../docs/TESTING.md`](../../docs/TESTING.md) 체크리스트로 최종 확인 → push |
| push 후 | Jenkins/GitHub Actions CI 결과 확인 (`docs/CICD.md` §4 — ❌면 머지하지 않음) |

`frontend_develop`에 직접 커밋하지 않는다 — `feat/fe-*` 브랜치에서 작업하고 PR로
올린다 (`README.md` 브랜치 전략).

---

## 4. 막혔을 때

- 검증 루프에서 실패 → **그 단위 안에서** 고친다. 원인이 이전 단위에 있다면
  그 단위로 되돌아가서 고친 뒤 다시 앞으로 진행한다 (건너뛰지 않는다).
- 스펙 자체가 모호하거나 [`SPEC_FUNCTIONAL.md`](../../docs/SPEC_FUNCTIONAL.md)/
  [`WIREFRAME.md`](../../docs/WIREFRAME.md)와 충돌한다면, 코드로 임의로
  때우지 않고 **먼저 PM(사용자)에게 확인**한다.
